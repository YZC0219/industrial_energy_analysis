## 上一轮做了什么（2026-09-20，第 3 轮）

**#11「CUSUM 异常检测」+ 补完 #12**。前两轮做的 2σ 与产量基线都是**逐点**判据：
每一天独立地和基线比。这类判据对**缓变漂移**（设备劣化、换热器结垢）几乎无感——
每天只偏离 0.4σ，逐点看永远不超限，可半年积累下来就是一笔大钱。CUSUM 正是
为这种形态设计的：它累积**偏离量**，微小但持续的偏移会一直往上垒。

- 新增 **Q27** 与视图 `v_unit_energy_cusum`，给出 7 个车间 × 731 天的上下侧
  累积和序列。累积和用**闭式解** `S⁺ₜ = Cₜ − min_{0≤j≤t} Cⱼ`（`Cₜ = Σ(zᵢ − k)`）
  算，只需两个窗口函数（前缀和 + 前缀最小），**不用递归 CTE** —— 每个车间
  731 行、7 个车间，递归版会撞上 `cte_max_recursion_depth=1000` 的天花板。
- 报告「基线」节新增第三张图，三法并置；Q26 从两法对比扩成**三法对比**。

**三个不是照抄教科书的地方（答辩时的加分点）**：

1. **h=5σ 在本样本量下完全不可用**。教科书默认 `h=5σ`，但那是针对几百点以内的
   序列。本数据每个车间 730 点，用 5000 次白噪声仿真实测误报率：h=5σ 时
   **n=365 误报 52.3%、n=730 误报 77.4%、n=1461 误报 95.6%** —— 报警成了常态。
   所以判定限由仿真标定：取 `max(S⁺,S⁻)` 零分布的 **99 分位 → h = 9.9σ**。
   **这一步不能省**：h 必须随样本量重标，换数据量就得重跑仿真。
2. **累积前要先白化（whiten）**。CUSUM 有个前提是观测独立同分布，而单耗带着强
   季节性（冬夏差 61.6%）。直接累积的话，季节本身会把累积和推过阈值。做法是先
   减去「车间 × 日历月」的残差均值再累积。效果：连续型车间的最大累积和
   **平均砍掉 63.4%**（轧制 37.1→15.7、熔炼 32.1→10.8、热处理 32.7→10.7）。
   > 第 4 轮修正后：平均砍掉 **70.1%**（轧制 44.6→11.7、熔炼 37.2→11.0）。
3. **报警段长 ≠ 持续异常**。11 段平均 7.3 天，但拆开看 **10 段的第 1 天贡献了
   该段 Σ|z| 的 84%~100%**（⚠️ 此数字已被第 4 轮修正为 **53%~100%**，见上方
   修正说明）—— 长度来自 CUSUM 的衰减速度（每天只回落 k=0.5σ，
   一个 −11σ 的日子要好多天才消下去），不是因为这十几天都在异常。
   所以「压成 11 段」这个说法本身是误导，报告里没有用它当卖点。

**量化结论（全部由脚本从数据算出，不写死）**：

| 指标 | 2σ 固定阈值 | 产量基线 | CUSUM |
|---|---|---|---|
| 检出（天 / 点） | 251 | 49 | 80 天（11 段）|
| 检出中节假日占比 | 75.3% | 22.4% | 见下方逐段归因 |
| 能抓的异常形态 | 单日大偏离 | 产量/季节解释后的偏离 | **缓变漂移**（前两者都漏）|

**11 段报警逐条归因到了根因（100% 覆盖）**，没有一段是"说不清"的：

| 归因 | 段数 | 涉及车间 | 具体日期 |
|---|---|---|---|
| ETL 丢行（清洗剔除后未回填） | 3 | 熔炼 / 轧制 / 热处理（全是连续型） | 2025-03-23、2024-12-29、2024-03-16 |
| 日历（节假日 / 周末） | 8 | 机加工 / 表面处理 / 装配 / 包装（全是间歇型） | 元旦、春节、端午、中秋、除夕 + 3 个周末 |

方向也正好按车间类型劈成两半：**持续偏低 3 个全是连续型车间，持续偏高 4 个
全是间歇型车间**。前者是丢数据把当日能耗拉低，后者是假期只留基础负荷、
产量趋零而固定能耗仍在。

**发现：年际漂移在本数据里检不出来（是功效问题，不是实现问题）**。数据里注入的
单耗年降 3% 是**渐变**，正是 CUSUM 该抓的。实测前半程 vs 后半程的累积和落差只有
**0.04~0.36σ**，而阈值是 9.9σ —— 差一个数量级。只有一个车间（轧制）的 t 检验
p=0.014 勉强显著。**结论要如实写**：3%/年 在 730 天里摊到每天约 0.006σ，
本数据量与噪声水平下不可能检出。

**顺带修掉的一个真隐患**：Q16 是 `ORDER BY Z值 DESC LIMIT 50`，并列时
**不光行序不稳、连第 50 名卡在谁身上都不确定**（实测同一份数据两次跑出的
名次会换位）。已给 `analysis.sql` 里全部 24 条 `ORDER BY` 补上**唯一键做次序
键**（`ORDER BY Z值 DESC, 日期, 车间` 等），并连跑两遍确认输出逐字节一致。

## 上一轮做了什么（2026-09-20，第 2 轮）

**#10「考虑产量的能耗基线」+ #12 的对比部分**。原来只有固定阈值(25%)和
固定 2σ 两种判据，它们只看「比自己平时高多少」，不看**当天产量是多少**。
本轮补上按产量折算的期望值模型：

- 新增 **Q25**：每个车间用自己 731 天拟合
  `期望单耗 = a + b·ln(产量) + g·sin(2π·年内第几天/365) + h·cos(...)`，
  回归用正规方程 `(X'X)β = X'y` 在纯 SQL 里闭合求解（4 个参数，手写闭式解
  比引存储过程更可审计）。残差标准差用 `A + 2B` 方差展开式算，全是 SUM 聚合。
- 新增 **Q26**：固定阈值法 vs 产量基线法的**逐车间对比**（检出量、重叠度、
  节假日占比、噪声压低比），这就是 #12 要的对比实验主体，只差 CUSUM。
- 报告新增「**基线**」节：残差控制图（可切换车间）+ 两法对比表。

**量化结论（报告与本文都从数据算出，不写死）**：

| 指标 | 固定阈值 2σ | 产量基线 | 说明 |
|---|---|---|---|
| 总检出 | 251 天 | 58 天 | 基线把产量/季节解释掉后，绝大多数"异常"消失了 |
| 残差 σ / 原始 σ | — | 0.40 ~ 0.78 | 模型解释掉 22% ~ 60% 的单耗波动 |
| 检出中节假日占比 | 75.3% | 62.1% | 阈值法的"异常"大半是日历，不是跑冒滴漏 |
| 两法一致 | 56 天 | | 两法都认的更可能是真异常 |

单看间歇型车间更能说明问题：**装配车间**的 58 个阈值法超限日**全部**是节假日，
**表面处理** 56 个里 55 个是节假日，**机加工** 60 个里 57 个是节假日 —— 那是
假期只留基础负荷、产量趋零而固定能耗仍在，单耗自然抬高，不是故障。基线法对应
降到 18 / 4 / 15 天。

**过程中发现的两件事（下轮要注意）**：

1. **Docker 里的 MySQL 不会跟着 `output/*.csv` 自动更新**。本轮 `--check` 基线时
   报出 15 份"有差异"，数字只在末 1~2 位变化（如热处理 13080.72 → 13080.78），
   看起来像口径改了，其实是 **a0761f0 修完行尾后重新生成过数据、而容器里还是旧
   数据**。先 `--init --run-analysis` 重新装载，24 份基线与磁盘输出**立刻全部吻合**。
   **教训**：基线有差异时，先怀疑容器数据陈旧，再怀疑口径变了。
2. **少数残差会远低于主体**（热处理 min = -141.66，而 2σ 只有 31）。那是能耗贴到
   待机底、产量却非零的日子。让这 1~2 个点决定纵轴会把整个 σ 带压成纸带，所以
   报告把轴收到 σ 带附近、越界点画成**边缘三角**并标注天数，不静默丢数据。

## ✅ 已修复：清洗阶段「离群值连记录一起丢」

**问题**：`clean_data.py` 第 8 步剔除「消耗量离群」时写的是
`df = df.loc[~out_mask].copy()` —— **整行丢掉**。而第 10 步的缺失插补判据是
`df["consumption"].isna()`，只认「原本就是 NaN 的行」，看不到被丢掉的那些行。
**两者对不上，被剔除的格子就永久缺失了，插补根本不会触发。**

后果不是「少了一个数」而是「少了一个能源品种」：丢掉 E02（天然气，占当日
tce 约 70%）后，该车间当天只剩 3 个品种，当日总能耗直接掉七成，分析层把它
读成一次真实的能耗骤降（单耗残差冲到 **−11σ**），在 CUSUM 里表现为持续偏低
报警。**即清洗脚本自己造出了数据里并不存在的异常。**

**改法**：`df.loc[out_mask, "consumption"] = np.nan`（置空而不是删行），
让第 10 步的插补按（车间×能源×月）中位数接住。语义上「这个**数值**不可信」
就该补一个估计值，而不是让这条记录消失。

## 用 Airflow 调度

上面的四步也可以交给 Airflow 编排 —— 依赖、重试、失败告警、调度周期都由 DAG 管，
不需要人盯着顺序。

```bash
docker compose up -d          # 首次会构建镜像, 约 2~3 分钟
# 打开 http://localhost:8080  账号 admin / admin
# 在 DAG 列表里取消 energy_pipeline 的 Pause, 点 Trigger
```

**前置条件**：Docker。Windows 上需要装 WSL2 + Docker Desktop（Airflow 官方不支持
Windows 原生运行）。

### 五个服务

| 服务 | 作用 | 挂载 |
|---|---|---|
| `postgres` | Airflow 自己的元数据库（DAG 状态、任务实例） | `postgres-db` 卷 |
| `mysql` | 项目的分析仓库（星型模型 + 29 条查询跑在这里），映射到宿主机 `3307` | `mysql-data` 卷 + `./output`（只读）|
| `airflow-init` | 一次性任务：建元数据库表 + 建管理员账号，跑完即退 | — |
| `airflow-scheduler` | 调度器 | `./dags`、`./`（项目目录）|
| `airflow-webserver` | Web UI，`localhost:8080` | 同上 |

元数据库用 Postgres 而非复用 MySQL，是因为两者职责不同：一个是调度器的内部状态，
一个是业务数据。混在一起的话重建业务库会连调度历史一起清掉。

**为什么 mysql 也要挂 `./output`**：装载用的是 `LOAD DATA LOCAL INFILE`，
语句里那个文件是 **MySQL 服务端**打开的，不是执行脚本的 airflow 容器。
两个容器的文件系统互相看不见，不在 mysql 这边挂上、且路径与 airflow 侧对齐
（都挂到 `/opt/airflow/project/output`），服务端就会报 `File not found`
并静默装入 0 行。只读挂载足够 —— 这个目录 mysql 只读不写。

### DAG 结构

```
generate_raw_data → clean_data → load_warehouse → run_analysis → build_report
```

- **幂等**：`load_warehouse` 走的 `create_table.sql` 用 `DROP TABLE IF EXISTS` 重建表，
  所以整条管道重跑任意次结果一致，不会数据翻倍。
- **并发控制**：`max_active_runs=1`。管道是全量重建，两次运行并发会互相覆盖。
- **重试**：失败自动重试 2 次，指数退避（1min → 2min → 4min）。数据库冷启动没就绪
  这类瞬时故障不该让整条管道挂掉。
- **告警**：`on_failure_callback` 里留了钩子，接 Slack/钉钉只需替换成 webhook 调用。
- **不回补**：`catchup=False`。全量重建的管道回补历史没有意义。

任务切分、每个任务的职责说明写在 `dags/energy_pipeline_dag.py` 的 docstring 里，
在 Airflow UI 的 Graph 视图点开 DAG 就能看到。

### 关键口径

- **折标煤系数** 取 GB/T 2589-2020《综合能耗计算通则》当量值, 如电力 0.1229 kgce/kWh、天然气 1.3300 kgce/m³。
- **碳排放因子**: 电力取生态环境部全国电网平均排放因子 0.5703 kgCO₂/kWh; 燃料取 IPCC 缺省值; 压缩空气属二次能源, 不重复计入碳排。
- **重复计算提示**: `W07 动力站` 属公用工程, 其产出的蒸汽被其他车间二次消费, 全厂口径会重复计算。能耗结构分析(Q01/Q04)用全厂口径, **单耗类分析(Q02/Q07/Q08/Q16/Q20)一律剔除公用工程**。

> **完整定义见 [`docs/指标字典.md`](docs/指标字典.md)** —— 每个指标的定义、单位、
> 口径与定义处都收在那一份里, 本节只留最常被引用的三条。
> 字典里的折标煤系数、CUSUM 参数、每条查询的口径归属由

## 清洗脚本做了什么

原始 CSV 刻意注入了 10 类质量问题, `clean_data.py` 逐一处理并留痕:

| 问题 | 处理方式 | 留痕文件 |
|---|---|---|
| 日期 4 种格式混用 | 逐一格式尝试解析, 全部失败则剔除 | `clean_rejects.csv` |
| 车间名/能源名 别名与错别字 | 别名表映射到标准编码 | — |
| 能源编码缺失 | 按名称回填 | — |
| 单位写法不统一 | 归一为能源主数据的标准单位 | — |
| 重复记录 | 按 日期×车间×能源 业务键去重(非整行相等) | `clean_rejects.csv` |
| 消耗量离群 (10 倍级) | 按 车间×能源 分组 `Q3 + 3×IQR` **置空**(不删行), 交由下方插补 | `clean_rejects.csv`(留痕) + `clean_fixed.csv` |
| 负消耗量 (仪表倒走) | 取绝对值 | `clean_fixed.csv` |
| 消耗量缺失 | 按 车间×能源×年月 中位数插补 | `clean_fixed.csv` |
| 单价缺失或为 0 | 按 能源×年月 中位数插补 | `clean_fixed.csv` |
| 费用 ≠ 量×价 (偏差>5%) | 以 量×价 重算 | `clean_fixed.csv` |

清洗后输出 `output/clean_report.txt` 报告, 记录每一步的处理条数与数据保留率。

> **「剔除」与「置空」是两回事, 别混**（第 4 轮踩过坑, 现在写死）：
> - **整行剔除**只用于记录本身不可用 —— 缺日期/缺车间/缺能源品种(没有分组键,
>   无法修补), 或业务键重复(同键多条, 只能留一条)。这些行进 `clean_rejects.csv`,
>   计入报告的【剔除】合计。
> - **单格置空**用于数值不可信 —— 离群值, 以及转不动的脏值。记录本身是好的,
>   只是那个数不能用, 置空后交给插补补一个估计值。这些进 `clean_fixed.csv`。
>
> `clean_rejects.csv` 里同时保留了 34 行**离群留痕**(带原始数值, 供事后回看
> "这条为什么被改写"), 但它们**没有被删除**, 所以不计入【剔除】合计 ——
> 报告里【剔除】的合计取的是 `stats['剔除-合计']`, 不是 `len(rejects)`。

### 落盘时的两个约定

改 `clean_data.py` / `generate_data.py` 的输出部分时注意:

- **行尾固定为 LF**: 所有 `to_csv` 都显式带 `lineterminator="\n"`。不指定的话
  pandas 跟着操作系统走(Windows 出 CRLF、Linux 出 LF), 而下游 `LOAD DATA` 的
  行终止符只能写死一个 —— 行尾对不上时整个文件会被当成一行, 静默装入 0 行。
- **BOM**: 用 `encoding="utf-8-sig"` 写, Excel 双击打开中文表头才不乱码。
  读取侧(`import_mysql.py`、`make_report.py`)相应地也用 `utf-8-sig` 打开。

## 数据生成逻辑 (业务规则)

生成的数据不是随机数, 而是带业务规律的, 可用于验证分析结果是否符合预期:

- **生产日历**: 连续型车间(熔炼/轧制/热处理/动力站)全年不停产; 间歇型车间周日与法定节假日基本停产。
- **待机损耗**: 停产日仍保留 `standby` 比例的基础负荷。
- **能耗随产量同步变化**: 能耗 = 负荷形状 × 产量年趋势 × 单耗年趋势, 因此能耗增速 = 产量增速 + 单耗增速。

随机种子固定为 `20240918`, 数据可复现。下表是当前数据下的**实际跑出结果**, 可作为回归基线:

| 业务规则 | 预期 | 实际结果 | 对应查询 |
|---|---|---|---|
| 产量年增 5%, 单耗年降 3% | 能耗同比 ≈ +1.9% | +1.31% | Q06 |
| 单耗年降 3% | 各车间单耗同比 ≈ -3% | -2.26% ~ -3.88% | Q08 |
| 天然气冬季采暖 | 与气温强负相关 | r = **-0.9555** | Q12 |
| 蒸汽冬季高 | 与气温强负相关 | r = **-0.9262** | Q12 |
| 电力冬夏双高峰 | 呈 U 形, 线性 r 偏弱 | r = 0.1738, 分档可见 U 形 | Q11 / Q12 |
| 间歇型车间停产日仍有基础负荷 | 可检出待机损耗 | 表面处理车间 58 天 / 110.89 tce | Q13 |
| 季节峰谷差约 20% | 环比 > 25% 属异常 | 检出 5 条, 集中在 11 月 | Q22 |
| 2024-2025 全厂 | — | 63,759.63 tce / ¥2.15 亿 / 156,783.46 tCO2 | Q01 |

> Q12 的相关性也更强（天然气 -0.9507→-0.9555、蒸汽 -0.9052→-0.9262），

这类缺陷单步测试全都看不见，实测也确实踩过（见「一个必须遵守的流程」）。
它慢是因为要真的从零跑一遍五个阶段，且用 `preserve_outputs` 备份还原
`data/`+`output/`，**不会污染工作区**。

`tools/verify_dag_run.py` 是同一套断言的**编排层**版本：不直接调脚本，而是
触发 Airflow DAG 让调度器去调，额外断言五个 task 全 `success`。它不进 pytest
（慢且依赖 webserver 在跑），手动执行。判据是：**改的是脚本 → 跑 pytest；
改的是 DAG / docker-compose / 容器路径 → 跑 verify_dag_run.py。**

### 为什么要有这些测试

这个仓库后续要动的是**装载逻辑、表结构、口径视图** —— 这三件事做错都不会
报错，只会让数字悄悄变。测试是给这些改动准备的护栏。

`test_clean_data.py` 里的 `TestCleanArtifacts` 和 `test_analysis_snapshot.py`
是**回归基线**：前者守清洗产物的业务键唯一性/无负值/费用口径，后者守 29 条
查询的每一行数字。基线在 `tests/baseline/`。

`test_metric_dictionary.py` 是**文档一致性测试**，与上面两类都不同：它守的是
`docs/指标字典.md` **不会跟着代码偷跑**。改了折标煤系数或 CUSUM 的 h，代码
跑得好好的，字典却还写着旧值，**没有任何东西会报错** —— 这份测试就是那个
会报错的东西。它从代码读真值再比对，而不是从字典抄一遍（抄了字典改错测试
也跟着错）。它**不校验**字典里的推导性实测值（如"天然气占比 49.24%"这类由某次
运行算出的快照），换数据就该变，写进测试只会变成需要天天维护的假绿。

> 但它**要**锁「口径速查表」里那两个基准数字（全厂 63,759.63 tce / 剔除后
> 46,400.52 tce）—— 它们是字典作为权威口径表的立论基础，必须与 Q01/Q02 基线
> 逐位一致。这条断言是 #17 补上的，起因就是发现它们曾静默漂移成
> `63,759.70` / `46,400.59`（见上）。

> **查询的排序必须是全序**。基线是逐字节比对，所以 `ORDER BY` 只写一个可能并列的
> 值（如 `ORDER BY Z值 DESC`）会让行序在两次跑之间漂移，甚至改变 `LIMIT` 截到谁。
> 全部 24 条 `ORDER BY` 现已补上唯一键做次序键。改查询时请沿用这个习惯。

### 基线过期了怎么办

如果改动是**有意**改变业务口径（比如统一公用工程口径后单耗数字本就该变）：

```bash
python tests/update_baseline.py --check   # 先看差异
python tests/update_baseline.py           # 确认无误后更新
```

然后**在提交信息里写明为什么变、变了多少**。

但要先分清**两种**"基线有差异"，它们的动作相反：

| 情形 | 判断依据 | 正确动作 |
|---|---|---|
| **数据/环境陈旧** | 说不出数字为什么该变；重新装载后差异消失 | **重新装载**（`--init --run-analysis`），基线不动 |
| **口径有意变更** | 能逐条说清每个数字为什么该变、变了多少 | **更新基线**，并写明原因 |

"别用刷新基线把问题盖过去"针对的是**说不出原因**的情形（那是 bug，不是基线过期）。
只要确认了口径变更，更新基线就是正当且必需的动作 —— 不更新，红线会一直红着，
红线本身也就失效了（详见 `docs/问题发现与工程复盘.md` 案例 4）。

### 历史修正怎么落地（upsert）

事实表的唯一键是 `(record_date, workshop_code, energy_code)`，它只标识
**哪条业务记录**，不标识**哪个版本**。因此上游修正一条历史记录后重新装载，
如果装载用 `INSERT IGNORE`，新版本会被当成唯一键冲突**静默丢弃**，库里
永远停在旧值上。

现在事实表装载走 **upsert**：先 `LOAD DATA` 进一张临时表，再
`INSERT ... SELECT ... ON DUPLICATE KEY UPDATE`，并且**每个业务列都套一层
`IF(new.updated_at > t.updated_at, ...)`** —— 只有严格更新的版本才覆盖。

- 只靠 `ON DUPLICATE KEY UPDATE` 会**无条件覆盖**，那样重放一批更旧的数据
  （比如补跑历史区间）会把后来的修正全部抹掉。判新旧这个条件是关键。
- `updated_at` 列本身用 `GREATEST` 保留最大值，避免被旧值拉回去。
- 服务端没开 `local_infile` 时，降级用的批量 `INSERT` 分支走同一条 upsert 逻辑。

对应的护栏是两条测试：`test_historical_correction_is_applied`（更新的版本
能覆盖）和 `test_stale_version_does_not_overwrite`（过期版本不得回退）。

`fact_production` 与 `dim_calendar` 仍用 `INSERT IGNORE`：它们没有历史修正
需求。若将来产量也要修正，给表加一个 `updated_at`，然后
`load_csv(..., upsert=True)` 即可复用同一套逻辑。

### 关于 `local_infile`
它需要在**服务端**开启 `local_infile`, 两种跑法各自的开启方式不同:

| 跑法 | 怎么开 |
|---|---|
| 直接用本机 MySQL | 在 `my.ini` 的 `[mysqld]` 下加 `local_infile=1` 后重启服务 |
| 用 Docker Compose | 无需手工操作, `docker-compose.yml` 里 mysql 服务的 `command` 已带 `--local-infile=1` |

服务端没开时 `import_mysql.py` 会自动退化为批量 `INSERT`, 所以两种情况都能跑通。

> **容器环境的一个坑**: `LOAD DATA LOCAL INFILE` 里的文件是 **MySQL 服务端**
> 按自己的文件系统打开的, 不是客户端。所以 `docker-compose.yml` 里 mysql 服务
> 也挂载了 `./output`(只读), 且路径与 airflow 容器保持一致 —— 否则服务端会
> 报 `File not found`。宿主机直跑时不存在这个问题(客户端和服务端是同一台机器)。
