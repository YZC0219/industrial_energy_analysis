实时事件首版契约已放在 `streaming/schemas/energy_event.schema.json`，用于提前固定事件标识、事件时间、更新时间、修正和删除语义。离线质量门禁与单机 Kafka/Flink 窗口实验已落地；删除捕获、迟到事件侧输出、流批对账和流式质量检查仍未实现，不能把单机实验等同于生产实时链路。

## 离线质量门禁（已实现）

对 Great Expectations 与 Deequ 的取舍：Great Expectations 适合本仓库的 Python/pandas 清洗与 CI 栈，并能连接 pandas 或 Spark DataFrame；Deequ 构建在 Spark 上，适合大规模分布式校验，但要管理与 Spark/Scala 版本匹配的 JVM 依赖。当前仓库 Spark 为独立 Hive/Spark 环境、常规 CI 不启动 Spark，因此先选 GX 1.23.1 承担表内规则，在轻量 pandas 关系检查中处理跨表键匹配。若后续在 Spark 集群进行大规模校验，再以匹配该集群 Spark/Scala 版本的 Deequ 做性能评估，而不是在无 Spark 的 CI 中引入 JVM。

规则定义在 `quality/rules/energy_batch.json`，包含能耗明细和产量表的必需列/非空、复合业务键唯一、非负范围、状态枚举，以及能耗记录的车间-日期键必须存在于产量表。运行：

```powershell
python -m pip install -r requirements.txt
python tools/check_data_quality.py --energy output/clean_batch_energy.csv --production output/clean_batch_production.csv
```

门禁输出 `output/data_quality_report.json`，失败返回非零退出码；现已接入 Pages 构建工作流，报告作为 CI artifact 同批留存。跨表检查只验证键覆盖，不推断产量与能耗数值之间的业务因果关系。该实现是离线批质量门禁，不代表 Kafka/Flink 实时校验已经完成。

## Kafka + Flink 实时实验（单机基线）

`docker-compose.yml` 中的 `streaming` profile 增加单节点 Kafka 3.9.1（KRaft）与 Flink 1.20.2 JobManager/TaskManager；默认 `docker compose up` 不启动它们，也不改动 Airflow/MySQL 服务。Flink SQL 在 `streaming/flink/energy_window.sql`：按 `event_time` 生成 5 秒有界乱序 watermark，做 10 秒滚动窗口车间费用汇总，窗口费用达到 100 元写入 `energy-alerts`，Kafka sink 使用 exactly-once 事务。checkpoint 每 2 秒写入命名卷；超出 watermark 的迟到事件目前由 Flink 丢弃，不配置 late side output。当前 SQL 只处理 `UPSERT`，`DELETE` 捕获仍是下一项工作。

一键启动并执行真实 Docker 实验：

```powershell
python tools/run_streaming_experiment.py
```

脚本启动独立 streaming profile，发出事件时间偏移 `+1s, +5s, +3s` 的乱序样本，等待含窗口状态的 checkpoint，停止并重启 TaskManager，确认 Flink REST 的 restored-checkpoint 标记更新后再推进 watermark，最后校验 Kafka 告警和端到端延迟。成功后只停止 Kafka/Flink 容器，保留命名卷和实验 JSON；可用 `--keep-running` 留下容器，并通过 Flink UI `http://localhost:8081` 检查。手工停止方式：

```powershell
docker compose --profile streaming stop flink-taskmanager flink-jobmanager kafka
```

本机实测报告 `output/streaming_experiment.json`：单 broker/单 TaskManager、窗口 10 秒、允许乱序 5 秒；同一 W04 窗口 3 条事件（到达次序 `+1,+5,+3`）经 checkpoint 与 TaskManager 重启恢复后，汇总 `155` 元并产生 `HIGH_COST` 告警。最近一次推进 watermark 后到消费告警耗时 `3.023` 秒；恢复 checkpoint 编号及延迟等逐次数据以 JSON 报告为准。这只是单机功能/延迟基线，不代表 Kafka/Flink 高可用或生产吞吐评测。Compose 的 Kafka Connect 和数据卷为单节点实验配置，不作为生产部署参数。
