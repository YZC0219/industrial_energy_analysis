## 离线质量门禁（已实现）

对 Great Expectations 与 Deequ 的取舍：Great Expectations 适合本仓库的 Python/pandas 清洗与 CI 栈，并能连接 pandas 或 Spark DataFrame；Deequ 构建在 Spark 上，适合大规模分布式校验，但要管理与 Spark/Scala 版本匹配的 JVM 依赖。当前仓库 Spark 为独立 Hive/Spark 环境、常规 CI 不启动 Spark，因此先选 GX 1.23.1 承担表内规则，在轻量 pandas 关系检查中处理跨表键匹配。若后续在 Spark 集群进行大规模校验，再以匹配该集群 Spark/Scala 版本的 Deequ 做性能评估，而不是在无 Spark 的 CI 中引入 JVM。

规则定义在 `quality/rules/energy_batch.json`，包含能耗明细和产量表的必需列/非空、复合业务键唯一、非负范围、状态枚举，以及能耗记录的车间-日期键必须存在于产量表。运行：

```powershell
python -m pip install -r requirements.txt
python tools/check_data_quality.py --energy output/clean_batch_energy.csv --production output/clean_batch_production.csv
```

门禁输出 `output/data_quality_report.json`，失败返回非零退出码；现已接入 Pages 构建工作流，报告作为 CI artifact 同批留存。跨表检查只验证键覆盖，不推断产量与能耗数值之间的业务因果关系。该实现是离线批质量门禁，不代表 Kafka/Flink 实时校验已经完成。

## Kafka + Flink 实时实验（单机基线）

`docker-compose.yml` 中的 `streaming` profile 增加单节点 Kafka 3.9.1（KRaft）与 Flink 1.20.2 JobManager/TaskManager；默认 `docker compose up` 不启动它们，也不改动 Airflow/MySQL 服务。Flink SQL 在 `streaming/flink/energy_window.sql`：按 `event_time` 生成 5 秒有界乱序 watermark，做 10 秒滚动窗口车间费用汇总，窗口费用达到 100 元写入 `energy-alerts`，Kafka sink 使用 exactly-once 事务。checkpoint 每 2 秒写入命名卷。

`streaming/flink/energy_quality_routes.sql` 定义三个独立消费组和隔离 topic：`CURRENT_WATERMARK(event_time)` 已越过的事件写入 `energy-late-events`；`op=DELETE` 写入 `energy-delete-events`；可解析但违反能耗值/业务键规则的行写入 `energy-invalid-events` 并带 `quality_error`。新增 `energy_raw_quarantine.sql` 用 Kafka `raw` 格式读取原始 BYTES，以 Java UDF 严格验证 UTF-8，再由 `IS JSON OBJECT` 校验 JSON 语法；坏消息按 `quality_error`、源分区/offset 和可还原原始字节的 Base64 写入 `energy-malformed-events`。四个有类型的 JSON source 使用 `json.ignore-parse-errors` 保持作业运行；不能只开这一选项，否则坏消息可能静默丢失。DELETE 路径只处理上游明确发送的事件，不会探测 MySQL 物理删除。该原始字节路由只验证坏 UTF-8/JSON，尚不保证所有字段类型错误、schema 演进或跨消费组原子一致性。

实现依据为 Flink 1.20 的 [Raw 格式](https://nightlies.apache.org/flink/flink-docs-release-1.20/docs/connectors/table/formats/raw/)、[JSON 解析选项](https://nightlies.apache.org/flink/flink-docs-release-1.20/docs/connectors/table/formats/json/)与 [Kafka 分区/offset 元数据](https://nightlies.apache.org/flink/flink-docs-release-1.20/docs/connectors/table/kafka/)；其中 `json.ignore-parse-errors` 官方语义是跳过错误行或将错误字段置空，并非自动保存坏消息。

一键启动并执行真实 Docker 实验：

```powershell
python -m tools.build_flink_udf  # 需要本机 JDK 17 和已有的 flink:1.20.2 镜像；产物留在 D: 项目目录
python -m tools.run_streaming_experiment --output output/streaming_experiment.json
```

脚本启动独立 streaming profile，提交窗口、三个结构化路由和原始字节隔离 SQL 作业，发出事件时间偏移 `+1s, +5s, +3s` 的乱序样本，等待含窗口状态的 checkpoint，停止并重启 TaskManager，验证恢复标记、正常告警、迟到事件、显式 DELETE、无效值、坏 JSON 与坏 UTF-8 的隔离。五个作业使用 5 个 TaskManager slots，避免作业排队。坏字节由 `kafka-python` 直接发送，不能用会转码的控制台生产者代替；本地依赖和编译产物应留在 D: 项目目录。成功后只停止 Kafka/Flink 容器，保留命名卷和实验 JSON；可用 `--keep-running` 留下容器，并通过 Flink UI `http://localhost:8081` 检查。最近一次实跑报告为 `output/streaming_experiment_raw_20260926.json`。手工停止方式：

```powershell
docker compose --profile streaming stop flink-taskmanager flink-jobmanager kafka
```

2026-09-25 UTF-8 复跑实测：单 broker/单 TaskManager、窗口 10 秒、允许乱序 5 秒；同一 W04 窗口 3 条事件（到达次序 `+1,+5,+3`）汇总 `155` 元并产生 `HIGH_COST` 告警；TaskManager 停止后从已完成 checkpoint 9 恢复，迟到事件、DELETE 和 `invalid_consumption` 隔离均得到各自 topic 的确认，中文 `record_status` 保持“正常”。告警消费延迟为 `5.575` 秒（本实验从发出重启后新窗口事件到读取匹配 `window_start` 的告警），报告：[UTF-8 复跑报告](../output/streaming_experiment_20260925_utf8.json)。该结果只是单机功能/延迟基线，不代表 Kafka/Flink 高可用或生产吞吐评测。Compose 的 Kafka broker 与数据卷为单节点实验配置，不作为生产部署参数。

2026-09-26 原始字节复跑：坏 JSON 和含非法 UTF-8 的 JSON 分别进入 `energy-malformed-events`，记录源分区 `0`、offset `70/71`、错误类别和原始字节 Base64；同次实验的窗口告警延迟 `5.696` 秒、checkpoint `13` 重启后恢复，其他三条隔离路由仍通过。机器可读证据见[原始字节复跑报告](../output/streaming_experiment_raw_20260926.json)。这些 offset 只对当次单节点 topic 有效，不是长期业务主键。

## 流批对账（可复现离线入口）

`tools/reconcile_stream_batch.py` 接收从 Kafka 导出的 JSONL 事件和同一业务键范围的批次 CSV，按 `record_date × workshop_code × energy_code` 取 `updated_at` 最新版本，忽略完全相同的 event 重放，应用显式 DELETE，并比较消耗量、单位、单价和费用。报告含输入 SHA-256、差异计数和样例；event_id 同 ID 不同 payload、非法事件、批流缺键或指标不一致都会令退出码非零。

对账器现在按原始字节逐行读取导出文件：损坏的 UTF-8 与不合法 JSON 都记录行号、字节偏移及该行 SHA-256，继续检查后续事件，并生成失败报告（退出码 1）。报告不回显原始坏字节。此能力仅覆盖离线导出审计，不能称为 Kafka/Flink 在线反序列化隔离。

若同一业务键出现相同 `updated_at`、不同业务状态的事件，即使最终数值碰巧与批次相同，也作为 `version_conflicts` 失败；事件 ID 不能充当来源版本的先后顺序。相同版本、相同状态的不同事件 ID 可以视为等价重放。此检查不替代源端单调版本号或 CDC 日志顺序。

```powershell
# 先确保 Kafka 中已有完整、与批次快照同范围的事件历史，再导出：
docker compose --profile streaming exec -T kafka /opt/kafka/bin/kafka-console-consumer.sh `
  --bootstrap-server kafka:9092 --topic energy-events --from-beginning --timeout-ms 10000 `
  > output/energy_events.jsonl

python tools/reconcile_stream_batch.py `
  --events output/energy_events.jsonl `
  --batch output/clean_batch_energy.csv `
  --output output/stream_batch_reconciliation.json
```

两份输入必须代表同一业务键范围和同一截止时点；把仅含演示样本的 topic 与全量 batch CSV 直接比较会正确报差异。该工具是导出后的审计/对账，不是常驻 Kafka consumer，也不会自动修复差异。`output/stream_batch_reconciliation.json` 是运行产物，只有实际运行成功并核对范围后才能引用结果。

新增一条可重复的一次性 Kafka 快照入口：`tools/reconcile_kafka_snapshot.py` 在消费前冻结每个分区的结束 offset，要求保留历史从 offset 0 开始，导出到 D: 项目目录后自动调用上述对账器。为了避免“指标值没变但批次版本已过期”被判 PASS，它要求 `--batch-timezone` 明确解释 MySQL CSV 的无时区 `updated_at`，并将批次版本与流中最新版本逐业务键比对；批次 CSV 在导出期间变动也判失败。

```powershell
python -m tools.reconcile_kafka_snapshot `
  --topic energy-events --bootstrap 127.0.0.1:29092 `
  --batch output/clean_batch_energy.csv --batch-timezone Asia/Shanghai `
  --report output/stream_batch_reconciliation.json
```

只有该 Kafka topic 确实覆盖批次的完整业务键与修正/删除历史时，PASS 才能作为同范围快照证据。offset 0 只证明*留存的* Kafka 历史从头导出，不证明源端无漏发、无压缩清理；当前演示 `energy-events` 并非 MySQL CDC 全量来源，直接拿它对全量 `clean_batch_energy.csv` 验证应当失败。2026-09-26 使用独立的一行测试 topic 实跑通过，证据为[审计报告](../output/kafka_snapshot_smoke_20260926.json)、[冻结导出](../output/kafka_snapshot_smoke_20260926.jsonl)和[对应批次](../tests/fixtures/kafka_snapshot_smoke_batch.csv)。这只是入口验收，不代表生产流批自动调和或自动回补。


## 日期维表范围扩展

`clean_data.build_calendar(min_date, max_date)` 保留 2024-01-01 至 2025-12-31 的基准范围，并按本次全量能耗及产量事实数据的最早/最晚日期扩展；批量文件仍携带完整维表快照，MySQL 增量装载按幂等插入补齐新日期，并在写事实前校验批次日期落在维表最小/最大日期之间。新增早于 2024 或晚于 2025 的数据会自动获得日期维记录。节假日名称目前只维护至 2025 年，后续年份仍需补充经确认的法定节假日数据。物理硬删除捕获未实现；Flink v1 的 UPSERT/DELETE 事件契约也不等同于 Kafka 持久删除处理。

## 软删除 tombstone

MySQL `fact_energy_consumption.is_deleted` 是保留删除事件的标记，表行仍保留原业务键和指标值；删除时将 `is_deleted` 设为 `1` 并把 `updated_at` 更新到当前增量窗口。MySQL 分析视图过滤软删除行，DataX 仍抽取 tombstone，DWD 合并时按业务键和 `updated_at` 选最新版本并保留 `is_deleted`，DWS 在能耗、费用和温度聚合中排除该行，ADS 随受影响日期重算。旧快照因版本时间较早不能覆盖 tombstone；更晚到达的有效 UPSERT 可以重新激活该业务键。Airflow 先执行幂等 MySQL 与 Hive schema migration。

```sql
UPDATE industrial_energy.fact_energy_consumption
SET is_deleted = 1,
    updated_at = GREATEST(NOW(), updated_at + INTERVAL 1 SECOND)
WHERE record_date = '2024-03-15'
  AND workshop_code = 'W04'
  AND energy_code = 'E01';
```

该标记必须保留到 DataX 对应 `updated_at` 半开窗口完成同步。物理硬删除、未更新 `updated_at` 的删除和从 MySQL 自动捕获硬删的 CDC 源仍未覆盖；生产源若只提供硬删除，需要 Debezium/binlog 等 CDC 日志或周期性全量对账。Kafka 中明确产生的 `op=DELETE` 事件由新增 Flink 路由保留，但这不等于 CDC 捕获已经建成。

## 阶段三剩余边界

- Flink late/DELETE/invalid 与原始坏字节路由已完成单机实跑；流批对账有一次性 Kafka offset 冻结导出入口，但尚无完整 MySQL CDC 事件来源、常驻调和或自动回补。
- 硬删除 CDC：仍需真实 MySQL binlog/CDC connector、schema 演进和重放测试；软删除 tombstone 与 Kafka 显式 DELETE 不能替代。
- 多节点高可用：当前 Kafka 单 broker、Flink 单 JobManager/TaskManager，不支持声称 broker 故障容忍或 HA。需要集群资源与故障注入验收。
- 流式质量已覆盖 SQL 可读字段规则以及坏 UTF-8/JSON 原始字节隔离；schema registry、所有类型转换失败的可追溯隔离、迟到数据回补 DWD/DWS 与流批自动调和仍是后续工作。
