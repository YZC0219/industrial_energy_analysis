# 阶段一：分层数仓与分布式计算

## 分层、粒度与血缘

| 层 | 表 | 粒度 / 逻辑主键 | 直接上游 |
|---|---|---|---|
| ODS | `ods_energy_consumption` | 源记录 / `id`，同步分区 `dt` | MySQL `fact_energy_consumption` |
| ODS | `ods_production` | 日期×车间；`dt=current` 当前全量快照 | MySQL `fact_production` |
| ODS | `ods_workshop/energy_type/calendar` | 各自然主键；`dt=current` 当前全量快照 | MySQL 三张维表 |
| DWD | `dwd_energy_consumption_detail` | 日期×车间×能源；SHA-256 代理键 | ODS 五表 |
| DWD | `dwd_production_detail` | 日期×车间 | ODS 产量、车间 |
| DWS | `dws_workshop_energy_day` | 日期×车间 | DWD 能耗、产量 |
| DWS | `dws_workshop_energy_month` | 月×车间 | DWS 日表 |
| ADS | `ads_factory_energy_day` | 日期 | DWS 日表 |

血缘为 `MySQL → DataX → ODS → Spark SQL → DWD → DWS → ADS`。DDL 在 `hive/ddl`，转换在 `spark/sql`。ODS 使用 DataX 官方预编译 HDFS Writer 原生支持的 ORC，DWD/DWS/ADS 使用 Parquet。该 Writer 不支持 ORC `DECIMAL`，因此 ODS 小数列按精确字符串落盘并在 DWD 入口显式转回规定的 `DECIMAL(p,s)`；更新时间仍以 `TIMESTAMP` 落盘，不牺牲版本精度。ODS 能耗事实的 `dt` 是同步批次日期；DWD、DWS、ADS 的日分区才是业务日期，月汇总按业务月分区。Hive 不强制主键，因此“主键”是质量门禁检查的逻辑约束。

## 部署与运行

依次执行 `hive/ddl/00..03`。Spark 客户端必须加载 Hadoop 配置，例如设置 `HADOOP_CONF_DIR=/usr/local/hadoop/etc/hadoop`；否则 `/warehouse/...` 会被误解析为本地 `file:` 路径。Airflow 容器需能访问 DataX、Spark/Hive 和 HDFS（可使用独立 Hadoop 集群并把客户端与配置挂载进 Airflow 容器），并配置 `MYSQL_USER`、`MYSQL_PASSWORD`、`MYSQL_JDBC_URL`、`HDFS_DEFAULT_FS`。字段映射由同步脚本统一维护。设置 `LAKEHOUSE_ENABLED=1` 后，新链路与原 MySQL 基线链路并行执行；默认关闭，避免普通本地环境因没有 Hadoop 而失败。

单机安装的参考环境如下，实际路径按部署调整：

```bash
export JAVA_HOME=/usr/lib/jvm/java-11-openjdk-amd64
export HADOOP_HOME=/usr/local/hadoop
export HADOOP_CONF_DIR=/usr/local/hadoop/etc/hadoop
export SPARK_HOME=/usr/local/spark
export HIVE_HOME=/usr/local/hive
export PATH="$JAVA_HOME/bin:$HADOOP_HOME/bin:$HADOOP_HOME/sbin:$SPARK_HOME/bin:$HIVE_HOME/bin:$PATH"
```

日常增量以 Airflow 的 `[data_interval_start, data_interval_end)` 过滤 `updated_at`。维表与产量体量小，统一全量覆盖唯一的 `dt=current` 快照，避免每天复制一份相同维表；能耗事实按同步批次日期写入 `dt={{ ds }}`。Spark 从该同步批次提取所有受影响的 `record_date`，把对应业务日期的 DWD 旧快照与新版本合并，按完整 `updated_at` 去重，再动态覆盖这些业务日期。DWS 日表重算受影响业务日；月汇总先识别受影响月份，再扫描月份的全部日汇总；ADS 先识别受影响日期，再扫描这些日期的全部车间汇总。每次 `INSERT OVERWRITE` 都以完整目标分区为输入，避免部分批次聚合覆盖整月或全厂日结果。因此历史修正不会因 `record_date != ds` 被丢弃。

首次初始化前，先按 README 快速开始生成并全量装载 MySQL 的完整 2024–2025 快照；再用专用入口连续完成全量同步和全历史分层构建。`--biz-date` 只是本次全量快照的 ODS 分区标签（选数据快照日期，如 `2025-12-31`），不是筛选源日期的条件。首次 DWD 读取 ODS 全部 `dt` 并动态创建所有业务日分区；合并工作表同时记录批次标签，之后的增量只消费该批次。不能全量写入后立刻触发同日常规增量 DAG；后者会以相同 ODS 分区执行 `truncate`，空窗口可能覆盖刚写入的全量批次：

```bash
python tools/bootstrap_lakehouse.py --biz-date 2025-12-31
```

之后才切换到 Airflow 的半开更新时间窗口。无新增或修正记录是合法空批次，质量门禁检查“本批 ODS 键均已进入合并结果”，不会把空批次误报为故障。需要确保 Airflow 处理的 `ds` 与 ODS 增量批次日期一一对应；补数按同一逻辑日期重放。当前链路是更新时间增量而非删除 CDC；源端物理删除不会自动传播，若有删除需求需增加 tombstone 字段或定期执行全量对账。

真实集群验收已在 Ubuntu VM（2 vCPU、8 GB、Spark 3.5.1、Hive 3.1.3、Hadoop 单节点）完成。全量链路读取 19,006 条能耗事实，生成 19,006 条 DWD 能耗明细、5,848 条 DWD 产量明细、5,848 条车间日汇总、192 条车间月汇总和 731 个全厂日分区；DWD 批次覆盖、非空、唯一、必填、产量唯一以及 DWS 对账、分区覆盖门禁全部通过。首次全量 DWD/DWS/ADS 墙钟时间分别为 353.690、206.166、160.278 秒。

迟到修正使用源记录 `id=1071`：业务日期保持 2024-03-15，将 `updated_at` 推进到 2026-09-23。增量批次写入同步分区后，DWD 值从 7227.234/24683.45 更新为 7237.234/24717.60，W02 日汇总从 18.9287 tce/62622.87 元更新为 18.9420 tce/62657.02 元，全厂日汇总从 96.2502 tce/318785.12 元更新为 96.2635 tce/318819.27 元；随后恢复源业务值并用新 `updated_at` 重跑，三层均恢复原指标，所有门禁再次通过。最终增量 DWD/DWS/ADS 两次成功耗时分别为 85.831/54.348/31.706 秒与 87.432/56.249/31.061 秒。调试期间两次被主动终止的慢查询也保留在原始性能日志中（`exit_code=143`），对应修复是关闭该查询的广播/AQE 路径并使用确定性 shuffle join。

三引擎各导出 5,848 行日×车间结果；与 pandas 基线相比，MySQL 与 Spark 的复合键完全一致，四项指标最大绝对误差均小于 `0.01`。完整机器可读证据保存在 `output/spark_performance.jsonl`、`output/engine_comparison.json`、`output/lakehouse_validation.json` 和三份 `*_daily.csv`。本次只完成 1× 单节点基线；10×/100×、多 executor 与重复中位数曲线仍属于后续扩容实验，不在本次结果中虚构。

补数使用 Airflow 的逻辑日期重放对应同步窗口，例如：

```bash
airflow dags backfill energy_pipeline --start-date 2025-01-01 --end-date 2025-01-31
```

`max_active_runs=1` 防止同表分区覆盖冲突。补数顺序仍由 ODS→DWD→质量门禁→DWS→质量门禁→ADS 保证；任何门禁失败都会停止发布并调用 `ENERGY_ALERT_WEBHOOK`。修复源数据后，清除该日期失败任务并重跑即可。

## 一致性与性能对比

核心口径沿用原模型：`tce=sum(consumption*std_coal_factor)/1000`，成本沿用清洗后的 `cost`，单耗为 `tce*1000/output_qty`。把 pandas、MySQL、Spark 的同粒度 CSV 导出后执行：

```bash
python tools/compare_engine_results.py --pandas output/pandas_daily.csv --mysql output/mysql_daily.csv --spark output/spark_daily.csv --keys record_date,workshop_code --metrics tce,co2_t,cost_yuan,unit_energy_kgce --atol 0.01
```

工具检查行数、复合键和最大绝对误差，失败返回非零；Spark 每个作业的墙钟时间写入 `output/spark_performance.jsonl`。性能试验应分别预热一次，再对 1×、10×、100×数据各运行至少三次，报告中位数及 Spark executor 数、shuffle 分区数、输入行数；小数据上 Spark 启动开销通常会使其慢于 pandas/MySQL，规模扩大后的吞吐趋势才是本阶段验证重点。

## 失败策略

- DataX 设零容忍脏记录；凭据只从环境变量注入，渲染后的临时配置在运行后删除。
- ODS 同步失败：不运行 DWD；用相同日期和窗口重跑。
- DWD 门禁：检查本批键覆盖、复合键唯一、必填/非负规则；合法空批次通过。
- DWS 门禁：DWD 与 DWS 的 tce 差小于 `0.01` 才发布 ADS。
- 告警：日志始终输出结构化 `[ALERT]`；配置 webhook 后同时发送 JSON，告警发送异常不会掩盖原任务异常。
