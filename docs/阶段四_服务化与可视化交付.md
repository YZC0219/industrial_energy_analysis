# 阶段四：服务化与可视化交付（进行中）

## 只读 FastAPI 指标服务

`src/api.py` 将已生成的 `output/Q*.csv` 暴露为只读 HTTP API，不直接连接 MySQL/Hive，也不在请求时运行分析 SQL。这样 API 的响应与可复现查询产物保持同源；更新数据需先成功运行仓库分析任务。`ENERGY_OUTPUT_DIR` 可覆盖默认 `output/` 路径。

启动：

```powershell
python -m pip install -r requirements.txt
python -m uvicorn src.api:app --host 127.0.0.1 --port 8000
```

本机访问 OpenAPI 页面：`http://127.0.0.1:8000/docs`；部署到可被其他机器访问的环境时，再按网络边界调整监听地址，并配置反向代理、认证和 HTTPS。当前版本面向本地/演示环境，不含用户认证、限流或多租户隔离。

| 路径 | 行为 | 主要来源 |
|---|---|---|
| `GET /health` | 检查指标、摘要和异常接口所需的关键产物是否存在 | Q01、Q02、Q03、Q16、Q22、Q28 |
| `GET /api/v1/metrics` | 按日期和车间筛选汇总能耗、费用、碳排 | Q28 |
| `GET /api/v1/anomalies` | 分页返回日单耗 2σ 异常与月度环比突增，保留指标类型和证据文件 | Q03、Q16、Q22 |
| `GET /api/v1/report-summary` | 返回全局 KPI、车间排名前五和异常数量 | Q01、Q02、Q03、Q16、Q22、Q28 |

日期过滤采用包含边界；月度环比告警按该月首日参加日期过滤。缺文件或字段无效返回 HTTP 503，不以零值掩盖过期/不完整数据；起止日期反转返回 HTTP 422。接口契约由 `tests/test_api.py` 覆盖，FastAPI 自动生成 OpenAPI schema。

`/api/v1/metrics` 的 `workshop_days` 是筛选后车间-日期行数，`record_days` 是这些行覆盖的不同日期数；`tce`、`cost_yuan`、`co2_t` 是所选车间日的加总。API 不返回跨车间产量总和：各车间产量单位不同，Q28 也未输出单位字段，直接合计会造成错误口径。`/api/v1/anomalies` 的 `total` 是经过日期/车间筛选后的总数，分页后再由 `offset` 和 `limit` 切片；日 2σ 与月度环比使用不同 `alert_type` 和 `period`，月告警事件日期标为月份首日，并通过 Q03 车间名映射编码。它们不是可互换的同一种异常标签。

PowerShell 调用示例：

```powershell
Invoke-RestMethod "http://127.0.0.1:8000/health"
Invoke-RestMethod "http://127.0.0.1:8000/api/v1/metrics?date_from=2025-01-01&date_to=2025-03-31&workshop_code=W04"
Invoke-RestMethod "http://127.0.0.1:8000/api/v1/anomalies?date_from=2025-01-01&date_to=2025-03-31&limit=50&offset=0"
Invoke-RestMethod "http://127.0.0.1:8000/api/v1/report-summary"
```

健康检查只检查所需文件是否存在，不判断文件是否新鲜、彼此是否来自同一次成功运行。业务接口的 `generated_at` 是所需文件中最新的文件修改时间，不是带批次 ID 的事务水位，因此不能用它证明产物原子一致。写入分析 CSV 时如果 API 同时在线，可能短暂读到新旧混合快照；当前演示用法应安排在上游任务成功结束后再查询，API 本身不需要重启。要面向生产，需要上游输出到版本化目录并以原子指针切换，或生成并校验带输入哈希的快照 manifest 后由 API 固定读取。

```powershell
python -m pytest tests/test_api.py -q
```

API 使用文件产物意味着它反映“最近一次成功生成的查询快照”，不是实时数据库查询。业务响应会带 `generated_at`（所需输入文件的最新修改时间）及可用的数据日期范围；服务部署仍需由上游调度负责刷新产物。

## Metabase 本地 BI（2026-09-25 运行时验收通过）

仓库提供可选 Compose `bi` profile，Metabase 使用独立 PostgreSQL 保存自身配置，BI 用户只读连接项目 MySQL。当前固定到官方发布的开源镜像 `metabase/metabase:v0.63.18`；启动后绑定宿主机回环地址 `127.0.0.1:3000`，不直接暴露到局域网。项目已有 MySQL 分析视图 `v_energy_enriched` 会排除软删除事实，BI 账号只获此视图的 `SELECT` / `SHOW VIEW`，不获得原始事实表权限或任何写权限。

首次启动步骤（保留现有 Docker Compose MySQL 数据卷；新增配置和浏览器验收文件均位于 `D:\industrial_energy_analysis`，Docker 镜像/卷使用已有的 D 盘数据目录）：

```powershell
# 只在尚无 .env 时运行；脚本生成随机 BI、Metabase 元数据库和演示登录口令，且不会覆盖旧文件
python -m tools.bootstrap_bi_local
docker compose --profile bi up -d mysql
# 授权脚本从宿主机连接现有 MySQL；以下只把 D 盘 .env 读入当前进程，不输出口令
Get-Content -LiteralPath .env | ForEach-Object {
    if ($_ -match '^([A-Z_]+)=(.*)$') {
        [Environment]::SetEnvironmentVariable($Matches[1], $Matches[2], 'Process')
    }
}
$env:MYSQL_HOST = "127.0.0.1"
$env:MYSQL_PORT = "3307"
$env:MYSQL_USER = "root"
$env:MYSQL_PWD = $env:MYSQL_ROOT_PASSWORD
python -m tools.setup_bi_reader
docker compose --profile bi up -d metabase-db metabase
```

打开 `http://127.0.0.1:3000` 完成 Metabase 管理员初始化，然后添加 MySQL 数据源：主机 `mysql`、端口 `3306`、数据库 `industrial_energy`、用户名 `energy_bi_reader`、密码取 `BI_DB_PASSWORD`。本机 MySQL 8 连接需要在附加 JDBC 选项填 `ssl=true&trustServerCertificate=true`，否则初次握手出现 RSA 公钥错误；此项只适用于当前 Docker 内网演示，生产环境需校验服务器证书，不应照搬 `trustServerCertificate=true`。BI 查询账号由脚本创建/轮换；执行脚本需要项目 MySQL 管理员凭据（`MYSQL_HOST`、`MYSQL_PORT`、`MYSQL_USER`、`MYSQL_PWD` 可覆盖）。账号主机默认 `%` 以适配动态 Docker bridge 地址；因此该配置仅适用于本机演示环境。跨机器部署前应限制 MySQL 网络入口，并把 `BI_DB_ACCOUNT_HOST` 收窄到固定可信网段/来源。

在 Metabase 中创建非管理员“能源只读”组，只允许对 `v_energy_enriched` 使用查询构建器，不给 SQL 编辑器或管理权限；公共集合给普通用户 View 而非 Curate 权限，样例集合不给权限。基于查询构建器创建按 `record_date`、`workshop_code` 聚合的费用图表，并把这两个字段同时映射到两张 dashboard 卡片。费用字段的全局格式设为 CNY。验收路径：按日期缩小区间、按车间筛选；点击一个车间柱形值，选择“查看此记录”，下钻到只读明细；使用该普通用户确认可以读视图、不能浏览事实表、写库、运行原生 SQL 或编辑看板。Metabase 的钻取要求底层数据集具有 query-building 权限；开源版不提供行列级用户隔离，因此项目层面的数据库账号仍是全体 BI 用户共用的最小权限边界。

启动配置可离线检查：`docker compose --profile bi config --quiet`；权限脚本和凭据引导由 `tests/test_bi_contract.py` 守卫。配置完成后运行 `python -m tools.verify_bi_runtime`：它从被 Git 忽略的 `.env` 读取本地演示用户，以普通用户验证只有一个数据库/视图/看板可见、两张卡片均映射日期和车间过滤器、原生 SQL 与看板编辑均被拒绝；再用 MySQL 只读账号验证源表读取和写入被拒绝，并比较 Metabase 与 MySQL 的筛选费用总额。报告写入被 Git 忽略的 `output/metabase_runtime.json`，不含口令或会话令牌。该脚本检验的是当前本机实例，不替代在新环境重新初始化、配置和运行。

### 操作检查与故障定位

```powershell
# 检查最终 Compose 配置、服务状态与 BI 启动日志
docker compose --profile bi config --quiet
docker compose --profile bi ps
docker compose logs --tail 100 metabase metabase-db

# 只停止 BI 容器，不停 MySQL/Airflow；不删除持久化卷
docker compose stop metabase metabase-db
```

| 现象 | 排查 |
|---|---|
| 页面不能打开 | 确认镜像拉取完成、`metabase` 容器启动；本配置只绑定 `127.0.0.1:3000`，从其他电脑访问会失败，这是刻意的默认安全边界。 |
| `metabase` 反复重启或数据库初始化失败 | 检查 `metabase-db` 健康状态、`METABASE_DB_PASSWORD` 在两个容器中一致、命名卷仍存在；不要用 `down -v` 排查，以免删除 Metabase 配置库。 |
| Metabase 测试 MySQL 连接失败 | 容器内主机名要填 `mysql` 而非 `localhost`，端口填容器端口 `3306`；确认项目 MySQL 已就绪且 `energy_bi_reader` 是脚本创建的同名账号。 |
| `SELECT` 被拒绝 | 以管理员重跑 `tools/setup_bi_reader.py`，确认分析视图已由 `sql/create_table.sql` 创建，数据库与账号环境变量正确。不要为了让连接变绿而直接授予 `industrial_energy.*` 或 `ALL`。 |
| BI 可以查表但看不到钻取菜单 | 给使用者授予该数据集的查询构建权限；钻取菜单依赖该权限。保持 SQL 编辑器权限关闭，避免绕过 UI 上的筛选和数据集边界。 |
| 数字和 HTML 报告不一致 | 确认服务读取的是同一份 `output/Q*.csv` 快照、刷新动作已在完整分析任务成功后进行；API 不运行 SQL，BI 则直接查询 MySQL 视图，刷新时间不同会造成短暂差异。 |
