## 统一指标定义与只读执行

语义版本升级到 2：29 个 `analysis_Q01`～`analysis_Q29` 为表格型指标，保留原 SQL 的排名、同比、相关系数、窗口基线和异常明细；7 个标量指标为综合/净能耗、单耗、综合/净费用、综合/净碳排放。不能把 29 个复杂分析强行变成可相加的数值。

每个分析绑定 SQL 块 SHA-256、输出列顺序、字段类型、单位和空值策略。SQL 改动后哈希不一致会拒绝读取，字段漂移、非有限数值也会失败。`tools/build_semantic_contract.py` 是显式刷新入口，从原 SQL 与基准产物生成契约；更新后应审阅 YAML、重新做快照和接口验收，API 不会静默刷新。

`governance/export.py` 从同一 MySQL REPEATABLE READ/READ ONLY 一致性快照执行全部 29 条分析，写入一个新的空目录，全部成功才生成 manifest；失败目录不能作为已验收版本发布。表格指标只接受原 SQL 的计算范围，传入日期/车间筛选返回 422，不把筛选后的旧窗口统计冒充重新计算结果。7 个标量仍支持日期/车间筛选；单位产品单耗仅允许单车间，不把不同产品产量直接相加。

## 坏消息隔离和人工修复回放

Kafka 消费默认保留“坏消息阻断”行为；显式传 `--quarantine-db` 才启用隔离。`streaming/alert_quarantine.py` 对非法 JSON、非法 UTF-8、空对象/非对象、NaN/Infinity 和 tombstone 保存原始 bytes（空值单独保留）、来源主题、分区、offset 和错误类型。记录按集群/消费组命名空间与 Kafka 位置去重，且绑定原队列目标；先提交本机隔离事务，再提交 Kafka 下一 offset。磁盘失败不会被吞掉，也不会推进消费进度。

```powershell
python -m streaming.kafka_outbox --bootstrap-servers localhost:29092 --topic <已授权主题> --group-id <专用消费组> --db D:/industrial_energy_analysis/output/alerts/redis-queue.sqlite --webhook-url http://127.0.0.1:8765/alerts --redis-url redis://127.0.0.1:6379/0 --quarantine-db D:/industrial_energy_analysis/output/alerts/quarantine.sqlite
python -m streaming.alert_quarantine list --quarantine-db D:/industrial_energy_analysis/output/alerts/quarantine.sqlite
python -m streaming.alert_quarantine list --quarantine-db D:/industrial_energy_analysis/output/alerts/quarantine.sqlite --include-raw
python -m streaming.alert_quarantine replay --quarantine-db D:/industrial_energy_analysis/output/alerts/quarantine.sqlite --queue-db D:/industrial_energy_analysis/output/alerts/redis-queue.sqlite --webhook-url http://127.0.0.1:8765/alerts --redis-url redis://127.0.0.1:6379/0 --id <隔离ID> --repair D:/industrial_energy_analysis/output/alerts/repaired.json
python tools/verify_quarantine_runtime.py
```

修复文件必须是人工给定的完整 JSON 告警对象。先持久化修复内容与 ID，标记 replay_pending，再入原队列，最后确认 replayed；中途失败可重放同一修复。已确定的修复不能换成另一份内容；原始消息不覆盖。回放只入队，不直接发送通知；自动解析/猜测修复内容未实现。该隔离入口检查传输/JSON 层合法性，并非所有工业设备字段与 schema 演进的业务校验。

实机报告 `output/extensions/quarantine_runtime.json`：7 条输入中 3 条正常告警、4 条隔离，最终提交 offset=7；首次隔离落盘后、Kafka 提交前强制退出，重启仍正确去重并保留 bytes/tombstone。人工修复第一条并回放两次，队列从 3 条增至 4 条。原默认阻断模式也已重新通过实际 Kafka 验收。

Kafka 提交进度语义依据：[KafkaConsumer 官方文档](https://kafka.apache.org/40/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)。

## 二元设备启停与工序约束

`optimization/equipment_schedule.py` 使用 SciPy HiGHS MILP，决策包括每设备每小时连续产量、二元开机状态、二元启动事件。约束覆盖需求守恒、小时能力、最短开机时长、最大启动次数、产量爬坡、全厂功率上限与工序累计物料平衡。下游只能使用上一小时及更早已完成的上游产量，流转比例为 1:1；开始前停机且无库存，末小时强制停机，禁止跨时域未完成的开机时长。

成本包含电量费用和启动成本，基准排程与优化排程执行相同约束检查。只接受求解成功且满足最优间隙条件的结果，超时或不可行不会返回成功排程。

```powershell
python -m optimization.equipment_schedule
python tools/verify_equipment_runtime.py
```

报告 `output/extensions/equipment_runtime.json`：模拟热处理与机加工各需 40 单位产量，基准运行费用 2,878 元，优化后 1,994.625 元，差额 883.375 元/日，mip_gap=0。独立重算产量、启停、最短运行、爬坡、功率、物料和费用；额外已知最优值算例为 0.2 元。不是实测节费，也不与旧连续分配模型的 860 元场景混用。

尚未包含真实设备参数、批次不可分割、最短停机时间、跨天初始运行状态、非 1:1 工艺良率、储能、需量收费和措施投资。真实实施需设备/工艺审核和同厂小时计量数据。

求解器依据：[SciPy milp 官方文档](https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.milp.html)。
