# CDC 可靠性专题：四周执行计划

计划基准：2026-10-20。四周按实际启动日计算，每周 5 个工作日；第 4 周另覆盖连续 7 个自然日的调度观察。计划不是已经执行的实验记录，不创建定时任务，也不启动服务。

## 目标和当前起点

围绕一条链路回答：重复投递、迟到修正、写入中断和消费暂停后，数据是否正确，如何恢复，代价是多少。

固定范围：隔离 MySQL 业务表 → Debezium/Kafka 单分区 → 完整 CDC 快照 → Spark DWD → DWS 日/月汇总 → ADS 工厂日报。验收终点为 ADS 表；网页报告和 API 发布另属消费链路，不纳入本轮成功声明。不增加模型或新的技术组件。

## 统一验收口径

**数据正确性**：不只看 sum。DWD 比较完整业务行、业务键唯一性、有效/删除条数、日期分区；DWS/ADS 比较完整分组结果、费用、标煤和碳排，必要时包括产量与单耗。所有精度和四舍五入按现有 SQL，独立期望值使用 Decimal。ETL 时间与业务列分开比较。

**部分成功**：保存 DWD、DWS、ADS、intent 和提交水位线的中间状态。当前多表写入不等于跨表事务；故障恢复前可能看到不同层版本，报告必须明确这个窗口，不能把最终重跑正确解释成全程原子可见。

**恢复耗时**：记录故障注入、恢复操作、connector 健康、Kafka 达到冻结目标边界、ADS 对账完成五个时间点。恢复耗时从恢复操作发起算到最终对账完成；总影响时间从故障注入算起。源写入结束后冻结明确边界，避免持续写入导致“追平”没有终点。固定积压规模下正式运行 5 次，报告中位数和范围，不预先承诺秒数。

**调度准点性**：区分数据区间/逻辑时间与真正应触发时刻；记录上海时区。进入观察前在 `acceptance.md` 冻结实验目标：在线且依赖正常时，预期触发时刻后 5 分钟内启动、30 分钟内完成。这是拟定实验门槛，需基准确认可行，不代表现有系统已达到。若不适用，应在观察开始前记录调整理由。

**窗口分类**：准点成功、迟到成功、在线失败、机器离线、计划维护、状态未知。分别报告计划总次数、有效在线次数及每类数量；在线失败和未知状态不能从统计中隐去。少量周样本只报告原始延迟及范围，不把它外推成年稳定性。

## 环境和实施前置条件

- 所有新增代码、数据、下载、缓存、证据放在 `D:/industrial_energy_analysis/` 下；现有远端执行目录记录映射，结果回收 D 盘。不改 Windows 或 Docker 全局存储设置。
- 故障只注入新的隔离库、主题、connector 和 DAG。主业务链路仅做只读定位；主业务 CDC 与旧 `energy_pipeline` 的竞争写入必须在运行清单中核对。
- `verify_cdc_scheduler_runtime.py` 当前硬编码远端 host/key 路径，且通过 Git bundle 只打包 HEAD。第 1 周先将实验所需位置改为显式参数，核对实际打包源码；不能以当前工作区改动推断远端已更新。
- `verify_cdc_business_warehouse.py` 的故障输出含固定 `output/fault.json` 等路径。并行或重复验收前改为每次独立的证据目录，避免把旧文件冲突当成预期注入失败。
- 所有新实验默认拒绝覆盖证据或复用命名空间。失败时保留状态，不以清空水位线、删除历史或重置基准使结果通过。

建议新增文件仅承担实验、测量与审计职责；生产实现只有在可复现问题证明需要时才修改。验证按 `energy-change-check` 技能选择，优先现有 CDC、软删除和新实验测试，在线与离线结果分别报告。

## 证据目录约定

后续每次运行使用 `D:/industrial_energy_analysis/output/reliability/<run_id>/`，下设实验输入、独立期望、事件、快照、故障前中后状态、分层对账、环境版本和日志。失败记录与成功记录同样进入总索引；不复制秘密配置。关键证据在专题结束时整理到本目录下的归档包，不能假设被 gitignore 忽略的 output 已随源码保存。

每次记录至少包含：experiment/run id、输入来源是真实或合成、隔离资源名、源码版本及工作区差异哈希、SQL 哈希、环境版本、故障注入点、起止时间、topic/partition/offset、源 binlog 坐标、intent/提交水位线、预期值、实际值、各项结论及未验证范围。
