## 1. 设计目标与约束

### 1.1 这是一个什么项目

面向工业企业的能源管理场景，把原始能耗数据加工成可用于决策的分析结果与
可视化报告。数据规模：**8 个车间 × 6 种能源 × 731 天**（2024-01-01 ~ 2025-12-31），
清洗后 19,006 条能耗明细 + 5,848 条产量记录，最终产出 29 组分析结果。

### 1.2 三条硬约束

这三条决定了后面几乎所有设计选择：

| 约束 | 含义 | 直接后果 |
|---|---|---|
| **数据是模拟的，但规律必须真实** | 没有真实企业数据，需要自己造；但造出来的数据必须带真实的业务结构（季节性的天然气采暖、连续型车间的待机底负荷、节假日停产） | 生成器不能是随机数，要按物理机理建模；异常检测方法才有意义 —— 否则在纯噪声上什么方法都能"检出" |
| **口径必须唯一** | "能耗"在不同上下文指不同的量（含不含动力站、算不算待机），同一个词混用会让结论互相矛盾 | 需要一份权威的指标字典（#7），并且口径本身要可验证 |
| **结论必须可复现** | 数字要能写进论文、经得起追问"这个数怎么来的" | 固定随机种子；查询结果落盘成快照；测试锁住每一行 |

### 1.3 一个说明性的取舍：为什么自己造数据

真实项目里第一步不存在（数据来自上游 ERP）。这里放在管道内，是为了让整条
链路**自包含**——`docker compose up` 之后能一键从零跑通，答辩现场不会卡在
"数据呢"。代价是生成器本身成了需要维护的组件，也意味着**清洗阶段处理的问题
是自己注入的**。这一点在论文里必须写明，不能伪装成真实数据质量问题。

## 2. 分层架构

```
┌─────────────────────────────────────────────────────────────┐
│  编排层   Apache Airflow + Docker Compose                    │
│           generate → clean → load → analyze → report         │
├─────────────────────────────────────────────────────────────┤
│  呈现层   自包含 HTML 报告（原生 JS/SVG，无外部依赖）          │
├─────────────────────────────────────────────────────────────┤
│  分析层   Q01~Q29 业务查询（SQL）                             │
│           + 三个异常检测算法（2σ / 产量基线 / CUSUM）          │
├─────────────────────────────────────────────────────────────┤
│  数仓层   MySQL 星型模型                                      │
│           3 维表 + 2 事实表 + 5 视图                           │
├─────────────────────────────────────────────────────────────┤
│  清洗层   clean_data.py（10 类质量问题，留痕）                 │
├─────────────────────────────────────────────────────────────┤
│  数据源   generate_data.py（固定种子 + 业务规律建模）          │
└─────────────────────────────────────────────────────────────┘
```

### 2.1 为什么分这几层

**分层是按"变更速率"切的，不是按技术栈切的**：

- **生成与清洗**一起变 —— 注入了新的脏数据类型，清洗规则就要跟着加。它们
  之间的契约是"10 类质量问题"。
- **数仓与分析**一起变 —— 加了维度就要改查询。它们之间的契约是**视图**：
  折标煤、碳排放、单耗这些派生量只在视图里算一次，分析 SQL 直接引用，不重复定义。
- **呈现独立于分析** —— 报告只消费 `output/Q*.csv`，不直接连库。所以换数据源、
  调 SQL 都不影响报告代码；反过来，报告改版也不用动 SQL。

### 2.2 一个刻意的"冗余"：视图 vs 查询

`v_energy_enriched` 把折标煤（`consumption × std_coal_factor`）和碳排放算出来，
而不是让 29 条查询各算各的。理由：**这两处换算每处都可能漏**——折标煤系数给的
是 `kgce`，业务口径要用 `tce`，中间有一次 `/1000`；单耗反向用 `×1000`。写成视图
后，29 条查询里一条都不会写错，改系数也只改一处。

## 3. 数据模型（星型模型）

### 3.1 表结构

| 表 | 粒度 | 行数 | 说明 |
|---|---|---|---|
| `dim_workshop` | 车间 | 8 | 含 `process_type`（工序）与 `is_continuous`（是否连续生产）|
| `dim_energy_type` | 能源品种 | 6 | 含折标煤系数、碳排因子、参考单价 |
| `dim_calendar` | 日期 | 731 | 周末/法定节假日标记 |
| `fact_energy_consumption` | 车间 × 日 × 能源 | 19,006 | 消耗量、单价、费用、气温 |
| `fact_production` | 车间 × 日 | 5,848 | 产量 |

### 3.2 两个维度字段承担了超出"描述"的职责

`dim_workshop` 的 `process_type` 和 `is_continuous` 不只是标签，它们**定义了
统计口径**：

- `process_type = '公用工程'` 标识出 W07 动力站。**全厂口径与剔除口径的差别
  就是这两个字**——动力站烧天然气产蒸汽，蒸汽又被其他车间消费，全厂口径会把这
  部分算两遍（详见 §4.1）。
- `is_continuous = 1` 标识全年不停产的车间（熔炼/轧制/热处理/动力站）。
  气温与能耗的相关性分析必须只看这些车间，否则停产日会把信号淹没。

> 把口径判据放在维度表里、而不是在每条 SQL 里写死车间编码，是为了让口径
> **可查询、可审计**：想知道"哪些查询剔除了公用工程"，搜 `process_type` 就行。
> `tests/test_metric_dictionary.py::TestScopeAttribution` 正是这么验的。

### 3.3 事实表的唯一键设计

`fact_energy_consumption` 的唯一键是 `(record_date, workshop_code, energy_code)`。

**它标识的是"哪条业务记录"，不是"哪个版本"** —— 这个区分在装载层（§6）有直接
后果：如果唯一键包含时间戳，同一条记录的历史修正就会变成新增行，事实表会膨胀；
如果不包含，历史修正又无法落地。当前设计配合 `updated_at` 做 upsert 解决。

### 3.4 五个视图的职责

| 视图 | 粒度 | 职责 |
|---|---|---|
| `v_energy_enriched` | 明细 | 附上折标煤、碳排放、单价参考价 |
| `v_daily_workshop` | 车间 × 日 | 日汇总（tce/co2/费用），带停产标记 |
| `v_monthly_workshop` | 车间 × 月 | 月汇总 + 单位产品能耗（单耗）|
| `v_unit_energy_baseline` | 车间 × 日 | 产量基线模型的期望值与**两套残差** |
| `v_unit_energy_cusum` | 车间 × 日 | CUSUM 累积和序列与报警判定 |

**为什么单耗在 `v_monthly_workshop` 而基线在视图里**：单耗的分子（能耗）与分母
（产量）在不同粒度上。月单耗 = 月能耗 / 月产量，可以直接算；但"日单耗的异常"
必须先建立产量—单耗的关系模型（§5.2），那是算法层的事，所以单独成视图。

## 4. 关键设计决策

### 4.1 统一能源统计口径（#7）

这是全项目最容易出错、也最需要文档化的地方。

**问题**：同一个词"能耗"在不同地方指不同的量。实测差别：
全厂口径 **63,759.63 tce**，剔除公用工程口径 **46,400.52 tce**，相差 **27.23%**。
报告里两种口径都要用（讲总量用全厂，讲单耗必须用剔除），混用会让读者得出
矛盾结论。

**三种口径**：

| 口径 | 判据 | 用途 |
|---|---|---|
| **全厂** | 含 W07 动力站 | 总量、结构、费用 —— "一共花了多少钱" |
| **剔除公用工程** | `process_type <> '公用工程'` | 单耗、异常检测 —— "真实用能是多少" |
| **仅连续型** | 再叠加 `is_continuous = 1` | 气温相关性 —— 排除停产日干扰 |

**为什么必须剔除公用工程**：动力站烧天然气产蒸汽，蒸汽被 W01/W02/W03/W05 消费。
蒸汽在动力站侧算一次折标煤，在消费侧又算一次 —— **全厂口径把 27.23% 的能算了两遍**。
凡是涉及"真实用能强度"的指标（单耗、异常检测）都必须剔除。

> **一个刻意的反直觉设计**：报告的**筛选器**（#14）走的是**全厂口径**，而不是
> 剔除口径。理由是报告"能源结构"一节的正文本身就在讲"全厂口径把动力站二次计入了"，
> 若筛选器悄悄换成剔除口径，一碰筛选 KPI 就会掉一块，与正文自相矛盾。所以筛选
> 前后是同一个口径 —— `Q28 求和 == Q01/Q03/Q05/Q14`，逐个核对过。
> 这是一处容易被后来者"修正"成 bug 的设计，`make_report.py` 与报告模板里都有注释
> 写明，`tests/test_end_to_end.py` 也锁住了这个恒等式。

### 4.2 异常检测：三个方法的递进（#9~#12）

不是"三个方法各做一遍"，而是**每一层修掉上一层的缺陷**：

| 方法 | 判据 | 修掉了什么 | 遗留缺陷 |
|---|---|---|---|
| **2σ 固定阈值** | `\|Z\| > 2`，逐日判 | —— | 不区分产量波动与真异常；节假日全被误报 |
| **产量基线** | 先拟合 `期望单耗 = a + b/产量 + 季节项`，再对**残差**取 2σ | 把产量因素分离出来，噪声压低 22%~39% | 仍逐日判，无法识别"缓慢漂移" |
| **CUSUM** | 累积和 `S⁺/S⁻` 越过 `h = 9.9σ` | 把多个散点聚合成持续段，可识别缓慢偏移 | 前提是观测独立同分布 |

**为什么顺序是这样**：2σ 是教科书方法，必须做（完成清单要求），但它在本数据集上
误报严重；产量基线是改进它的；CUSUM 是**另一种视角**（看累积而非瞬时），
恰好补上前面两者的盲区。Q26 给出三法的检出量/重叠度/误报结构对比，
报告里三图并置 —— 这个对比本身就是结论，不是附属品。

**CUSUM 的两个非平凡处理**（详见 `指标字典.md` §5.3）：

1. **必须先白化**：CUSUM 假设观测独立同分布，但单耗带强季节性。不消除季节，
   冬天的正常波动会被一路累积上去变成假报警。白化按**自然月**分组估计
   （不按"年+月"——那会把样本量砍半；年际差异属趋势，该由 CUSUM 抓，不该混进季节）。
2. **h 必须重新标定**：教科书默认 `h = 5σ`，那是对应 ARL₀ ≈ 300 天、为在线连续
   监控标定的。本项目是对 730 天历史做**一次性回顾**，同一门槛下误报率完全不同
   —— 实测 n=730 时 **77%** 的车间会至少报一次警。所以 h 由零假设仿真标定为
   **9.9σ**，`tools/calibrate_cusum_h.py` 保证这个结论可复核。

### 4.3 报告的动态筛选（#14）

**问题**：用户要按日期区间 / 车间 / 日型筛选，页面上的图要跟着重算。

**方案选择**：前端在浏览器里聚合，而不是每次筛选都回后端查库。原因是报告是
**自包含单文件**（可离线打开，答辩现场不依赖网络/服务）。

**关键设计：只传"可加量"**。报告不传"某车间某月的单耗"，而传
`(日期 × 车间 × 能源)` 的最细立方体（Q29，19,006 行）+ `(日期 × 车间)` 的
汇总（Q28，5,848 行），让前端自己按区间/集合求和。

**为什么不能传比例系数**：曾考虑"传一个费用/能耗比，前端乘一下"。实测全厂
费用/能耗的月际比值在 **3214~3658** 之间摆动 **13.8%**，不是常数 —— 乘一个比例
常数会算错。这条被否决的方案记在 `问题发现与工程复盘.md` 案例 2。

**为什么 Q29 用日度口径而非月度**：用户可能选一个跨月的区间，月度立方只能整月
计入，此时的合计必然与上方 KPI 对不上。只有到日这一层才能任意切区间。

### 4.4 清洗：留痕优先于清洗本身

`clean_data.py` 处理 10 类质量问题，但**输出的三份留痕文件比清洗结果更重要**：

| 产物 | 内容 |
|---|---|
| `clean_rejects.csv` | 被整行删除的记录（228 条重复业务键）|
| `clean_fixed.csv` | 被改写单元格的记录（1,220 条单位归一、383 条编码回填…）|
| `clean_report.txt` | 每步的处理条数与数据保留率（98.81%）|

理由：数据管道出问题时，你需要能回答"**这条记录去哪了**"。只有清洗后的数据、
没有留痕，就无法区分"这条记录本来就没有"和"被我清洗掉了"。

**一个真实教训**：清洗阶段曾用 `df.loc[~out_mask]` **整行删除**离群值，而插补
判据是 `isna()` —— 只看得见本来就缺的行，看不见被删掉的行。34 个格子永久缺失，
插补从不触发，下游把它读成真实的能耗骤降。修复是**置空而非删行**。
完整过程见 `问题发现与工程复盘.md` 案例 1。

## 5. 编排设计（Airflow）

### 5.1 DAG 结构

```
generate_raw_data → clean_data → load_warehouse → run_analysis → build_report
```

> **任务名以后者为准**。README 正文里曾写成
> `generate_data → clean_data → init_and_load_mysql → run_analysis → make_report`
> （是脚本名而非 task_id）。以 `dags/energy_pipeline_dag.py` 里的 `task_id` 为准：
> `generate_raw_data` / `clean_data` / `load_warehouse` / `run_analysis` /
> `build_report`。两者不一致时以代码为准。

| task | 做什么 | 产出 |
|---|---|---|
| `generate_raw_data` | 按固定种子生成带脏数据的原始 CSV | `data/raw_energy_data.csv` |
| `clean_data` | 10 类质量问题逐一清洗并留痕 | `output/clean_*.csv` + `clean_report.txt` |
| `load_warehouse` | 建库建表 + 装载进星型模型 | 3 维表 + 2 事实表 |
| `run_analysis` | 执行 29 条业务查询 | `output/Q01..Q29_*.csv` |
| `build_report` | 结果内联进模板 | `output/report.html` |

### 5.2 三个编排层的设计选择

**为什么元数据库用 Postgres 而不是复用 MySQL**：两个库职责完全不同——一个是
调度器的内部状态（DAG 状态、任务实例、变量），一个是业务数据。混在一起的话，
重建业务库会连带把调度历史清掉，而且两者的备份/恢复策略也不一样。

**为什么 `max_active_runs=1`**：管道是全量重建（`DROP TABLE IF EXISTS`），
两次运行并发会互相覆盖。

**为什么失败要自动重试**：数据库还没就绪、网络抖动这类瞬时故障不该让整条管道
挂掉。配 `retries=2` + 指数退避（1min → 2min → 4min，上限 10min）。
`load_warehouse` 单独给 3 次 —— 数据库冷启动可能还没就绪。

### 5.3 幂等性：靠 DDL 重建，而不是靠 upsert

当前 `load_warehouse` 走 `import_mysql.py --init`，执行的 `create_table.sql` 用
`DROP TABLE IF EXISTS` 重建所有表。所以**整条管道重跑任意次结果都一致**，不会
数据翻倍。

事实表**另外**做了一层 upsert（§6）——那是为历史修正准备的，与幂等是两件事。
DAG 文档里把"全量重建 → 增量装载 + 水位线"列为下一步改造方向：那时幂等要靠
`INSERT ... ON DUPLICATE KEY UPDATE` 保证，而不是靠 DDL 重建。

> 水位线**尚未实现**（完成清单 #4 是"与"不是"或"，upsert 做完不等于该项完成）。

## 6. 装载设计：upsert 与历史修正

### 6.1 问题

唯一键是业务键 `(record_date, workshop_code, energy_code)`，它不标识版本。
上游修正一条历史记录后重新装载：

- 用 `INSERT IGNORE`：新版本被当冲突**丢掉**，库里永远停在旧值。
- 用 `ON DUPLICATE KEY UPDATE`（无条件）：重放一批**更旧**的数据（如补跑历史
  区间），会把已有的新值**改回旧的**。

### 6.2 方案

每列都套 `IF(new.updated_at > t.updated_at, new.col, t.col)`：

```sql
col = IF(COALESCE(new.updated_at,'1970-01-01') > COALESCE(t.updated_at,'1970-01-01'),
         new.col, t.col)
updated_at = GREATEST(t.updated_at, new.updated_at)
```

- **每列判新旧**而不是只靠 ODKU：过期数据被正确忽略。
- **`updated_at` 用 `GREATEST`** 而不是直接赋值：被忽略的旧行不该把它自己那个
  更早的时间戳盖上去，否则该行的"最后修改时刻"会随重放倒退。
- **`COALESCE` 兜底空时间戳**：让"缺元数据"退化为"可覆盖"——语义上比"永远
  无法覆盖"更接近直觉。

### 6.3 装载路径与降级

主路径走 `LOAD DATA LOCAL INFILE`（比逐行 INSERT 快 1~2 个数量级）。若服务端
未开 `local_infile`，**自动降级**为批量 `executemany`，且降级路径同样做 upsert。

**一个踩过的坑**：降级判断最初无差别吞掉所有 `pymysql.err.OperationalError`，
导致"服务端读不到文件"这类真实错误也被当成"没开 local_infile"而静默失败——
任务报 success，后面分析查询全查空表。现在只对 `local_infile` / `not allowed`
两种错误降级，其余原样抛出。

> 还有两个只在 Docker 环境下才出现的静默失败（跨容器路径、CSV 行尾符），
> 记在 `问题发现与工程复盘.md`。

## 7. 数据流与产物契约

```
data/raw_energy_data.csv            (原始, 19,234 行, 含脏数据)
        │ generate_data.py
        ▼
output/clean_energy.csv    19,006 行 ┐
output/clean_production.csv 5,848 行 ├─→ import_mysql.py --init
output/dim_calendar.csv       731 行 ┘
        │
        ▼
    MySQL 星型模型 (3 维表 + 2 事实表 + 5 视图)
        │ import_mysql.py --run-analysis
        ▼
output/Q01..Q29_*.csv        (29 份快照)
        │ make_report.py
        ▼
output/report.html           (自包含, ~4.3 MB)
```

### 7.1 产物新鲜度的判据

**上游产物必须比下游旧**。判断方法：

```bash
ls -la output/Q01*.csv output/clean_energy.csv   # Q*.csv 必须比 clean_energy.csv 新
```

反了就意味着"张冠李戴"：报告是用上一轮的查询结果生成的。这条判据是**踩过坑
之后加的**（README 曾专门有一节讲它），现在由
`tests/test_end_to_end.py::TestArtifactFreshness` 自动守着。

### 7.2 三路自洽（端到端验收的核心不变式）

同一个合计有三条独立路径：

```
路径 A  Q01 直接聚合事实表
路径 B  Q28 车间日立方体求和        (前端 KPI 卡的底座)
路径 C  report.html 内联 JSON 的 totals.tce   (报告首屏显示的数)
```

**A == B 证"立方体没丢行/多行"；B == C 证"报告用的就是这份立方体"**。
实跑四路（含前端 KPI 底座）全是 `63,759.63`。

## 8. 被否决的方案

设计文档只写"选了什么"是不够的——**没写为什么没选别的，后来者会重新提议一遍**。
以下都经过实际评估并否决：

| 方案 | 否决理由 |
|---|---|
| 报告的筛选器改用"剔除公用工程"口径 | 与报告正文自相矛盾（正文讲的就是全厂口径的重复计算） |
| 前端传"费用/能耗比"系数再乘 | 该比值月际摆动 13.8%，不是常数，会算错 |
| Q29 用月度粒度 | 跨月区间下合计必然与 KPI 打架（案例 2）|
| 单耗基线用 `ln(产量)` 作基函数 | 机理上是 `1/产量` 的线性函数；换用后间歇型车间残差 σ 降 22%~39% |
| CUSUM 用教科书 `h = 5σ` | 本样本量下误报率 77%（案例 3）|
| CUSUM 白化按"年+月"分组 | 样本量砍半；年际差异属趋势，该由 CUSUM 抓 |
| 清洗阶段整行删除离群值 | 会让插补判据失效，34 个格子永久缺失（案例 1）|
| 加 `dim_product` / `dim_shift` 维度 | 已确认不在毕设范围内：会动星型模型 + 事实表外键 + 重新生成数据，**让全部 29 份基线失效**，且需手工重核报告正文所有写死的数字 |
| 用 REST API 做端到端验收 | 默认 `session` auth backend 让 API 全部 401；开通要改 `docker-compose.yml`——为了验收而改被测系统配置，验收脚本不该有这个副作用 |

## 9. 已知局限

诚实列出，论文里应如实说明：

1. **数据是模拟的**。所有"业务发现"验证的是方法链路的正确性，不是真实企业的
   用能规律。清洗阶段处理的是自己注入的脏数据。
2. **水位线未实现**（#4 部分完成）。当前靠 DDL 全量重建保证幂等。
3. **产品 / 班组维度未做**（#6 / #15，已确认不在范围）。
4. **异常详情联动未做**（#16 部分）：异常图悬停即显示该日单耗/μ/σ/Z 值/产量，
   表格视图列全部超限日，但缺"从告警区跳转到对应异常"的联动。
5. **CUSUM 的独立同分布前提**：白化按自然月消除了季节，但年际趋势与自相关
   残余仍可能影响判定限的标定精度。
6. **报告正文数字是手写死的**（讲结论的段落），改数据后必须逐个核对。
   这是 `docs/指标字典.md` 维护约定里明确警告过的风险类别。
