# 工业数据生命周期：四方向扩展 POC

四个方向均进入项目，复用原有数仓、Kafka/Flink、预测、质量及 API 能力。此页记录新增入口和验证边界，不能据此宣称已完成生产部署。新数据及缓存应显式落到 D 盘；远端 Spark 仓库路径由部署方指定。2026-10-02 的实跑复制现有 VM Spark 与现有容器 Java 到 D 盘，下载 Iceberg runtime jar 到 D 盘，并在 WSL 使用 `/mnt/d` 仓库和临时目录。随后下载 Redis/ClickHouse 验收镜像，镜像与原生卷均位于已确认的 `D:/Docker/wsl/disk/docker_data.vhdx`；客户端依赖和工程产物在本项目 D 盘目录。没有迁移原业务数据或安装系统包。

## 1. 实时监测、告警与分钟明细

- `streaming/simulate_power.py`：固定 45 分钟功率场景，第 20 分钟由 100 kW 升至 160 kW。默认 JSONL，显式提供 Kafka 地址才发送；发送是加速回放，不模拟真实分钟等待。
- `streaming/baseline_alert.py`：有限事件集按事件时间排序，15 分钟滑动均值超过固定基线 `100 + 2×10 kW` 触发告警，输出窗口内线性回归斜率。它验证计算口径，不实现 Flink watermark/CDC 撤回。
- `streaming/flink/power_baseline.sql`：Kafka 功率主题、30 秒 watermark、15 分钟窗口/1 分钟步长；输出均值、斜率、样本数到告警主题。现有 `energy_window.sql` 及其归档实机证据保持独立。
- `streaming/dispatch.py`：JSONL 告警预览，显式配置才写 Redis/投递 Webhook。Redis 保留 24 小时；请求携带稳定的 Idempotency-Key，但是否去重取决于接收端。失败返回非零，重跑可能重复投递。
- `streaming/minute_store.py`、`streaming/clickhouse.sql`：分钟均值与样本数，默认输出 JSONL，显式 ClickHouse HTTP 地址才插入。

```powershell
python streaming/simulate_power.py --output D:/industrial_energy_analysis/output/extensions/power_samples.jsonl
python streaming/minute_store.py --input D:/industrial_energy_analysis/output/extensions/power_samples.jsonl --output D:/industrial_energy_analysis/output/extensions/power_minutes.jsonl
```

不直接复用日能耗事件的 consumption 字段作为功率。连续功率采样的平均值也不是累计电表差分；缺样时不能直接宣称完整电量。样本计数不保证覆盖，真实采集需单独核验频率与唯一性。SQL 基线为 W01 演示值，需替换为审核的车间/时段基线；SQL 入口要求上游合法且去重的事件，非法数据应由现有隔离链路拦截。新 SQL 已在 Kafka 3.9.1 / Flink 1.20.2 单机实跑，20 个完整窗口的均值、线性回归斜率与样本计数均与独立参考值一致，W02 高负荷未进入 W01 告警。实跑修复了 `TIMESTAMP_LTZ` 与窗口时间做差的类型不兼容问题，显式 UTC 后统一类型。Kafka sink 未声明跨系统 exactly-once。

复现工具为 `python tools/verify_power_runtime.py`，需要先启动现有 Kafka/Flink 服务。工具创建独立主题，保留输入、输出、提交 SQL 和日志，最后只取消自身 job，不停止 Kafka。当前证据见 `output/extensions/power_runtime.json`。事件采用加速回放，末尾额外事件推进 watermark；此验收不代表分钟采样的真实端到端告警延迟。

## 3. 小时预测与分时电价优化

`optimization/forecast.py` 构建 100 天模拟小时数据，特征为预先已知产量计划、模拟天气预报、小时周期与周末。83 天训练、14 天验证，验证后用前 97 天重训，预测剩余 72 小时。用 Ridge 与 7 天季节朴素基线对照；已有日粒度 LightGBM/LSTM 实验继续保留。这里不会把日 tce 伪装成小时 kW。

`optimization/tou.py` 使用 SciPy HiGHS：决策变量为每小时可分配产量，目标是电量费用最小；约束为日产量守恒、小时生产能力、全厂功率上限和非负性。优化前校验原排程符合相同约束；不使用缺少约束的高费用基线夸大收益。总报告还将预测首日负荷减去原计划生产负荷，估算不可平移基础负荷并进入同一优化器。

固定演示场景：24 小时每小时原产量 5 单位，小时能力 15 单位，100 kW 基础负荷，20 kWh/单位，400 kW 上限。四档价格 0.35/0.70/1.10/1.40 元每 kWh 仅为示意，非某地区现行政策。演示日节费 860 元，按 30 个同样的运行日外推 25,800 元；预测闭环另有独立结果，不能混用。

模型允许连续分配产量，不处理设备二元启停、最短运行时间、爬坡、批次先后关系、储能、需量收费、不同产品工艺或改造成本。月收益是模拟情景外推，不是真实节费或投资回报。真实落地需同厂小时计量、排班、天气预报历史版本、电价及设备参数。

求解器依据：[SciPy HiGHS 接口](https://docs.scipy.org/doc/scipy-1.12.0/reference/optimize.linprog-highs-ds.html)。

### 持久化 Webhook 告警队列与重启恢复

`streaming/alert_outbox.py` 使用本机 SQLite WAL、FULL 同步和事务，告警按规范 JSON 的 SHA-256 去重。队列绑定通知目标的哈希，避免把已确认记录混用于另一个目标。工作进程领取带租约和随机令牌的记录，在数据库事务之外执行 HTTP 请求；过期租约可恢复，旧令牌不能确认新领取的记录。

网络故障、408/429/5xx 按指数退避重试，默认最多 5 次、间隔上限 300 秒。其他 HTTP 错误进入 dead 状态。失败记录与状态事件留存，可显式重新入队。当前不解析服务端 Retry-After，不自动清理历史记录；上线时需补充相应策略。进程退出后必须由运维服务重新启动 worker，队列本身不负责拉起进程。

```powershell
# 必须填写已授权的接收端 URL；以下仅为本机示例。
python -m streaming.alert_outbox enqueue --db D:/industrial_energy_analysis/output/alerts/queue.sqlite --input D:/industrial_energy_analysis/output/alerts.jsonl --webhook-url http://127.0.0.1:8765/alerts
python -m streaming.alert_outbox work --db D:/industrial_energy_analysis/output/alerts/queue.sqlite --webhook-url http://127.0.0.1:8765/alerts
python -m streaming.alert_outbox inspect --db D:/industrial_energy_analysis/output/alerts/queue.sqlite --webhook-url http://127.0.0.1:8765/alerts
python -m streaming.alert_outbox requeue --db D:/industrial_energy_analysis/output/alerts/queue.sqlite --webhook-url http://127.0.0.1:8765/alerts --id <dead告警ID>
python tools/verify_outbox_runtime.py
```

实际验收 `output/extensions/outbox_runtime.json`：独立子进程在接收端成功返回后、数据库确认前强制退出，重启自动恢复；该告警发送两次、接收端按 Idempotency-Key 只保留一次。503 暂时故障自动恢复，持续 503 三次后进入 dead，400 只尝试一次；人工重新入队恢复。共 9 次本机 HTTP 请求，3 个唯一成功告警，最终 sent=3/dead=1。原始 HTTP 尝试和事务审计保存在报告指定的 D 盘目录。

`streaming/kafka_outbox.py` 禁用 Kafka 自动提交，先提交 SQLite 事务，再提交下一条 Kafka offset；提交失败后的重放由队列 ID 去重。非法 JSON 会停止消费者且不提交进度，需要人工修复输入，默认阻断；可显式启用持久化隔离与人工回放，见三项纵深扩展说明。

2026-10-02 实际 Kafka 验收通过，入口 `python tools/verify_kafka_outbox_runtime.py`，报告 `output/extensions/kafka_outbox_runtime.json`。将已归档的 20 条真实 Flink 输出重新发布到独立测试主题，追加 1 条重复消息及 1 条坏 JSON。子进程完成首条 SQLite 落盘后、Kafka 提交前强制退出；消费组未提交进度。新进程重放后保留 20 条唯一告警，提交进度为 21，坏消息在 offset 21 阻断；再次启动仍阻断、不推进进度。随后 20 条落盘告警全部发送至本机 Webhook，接收载荷与原 Flink 输出逐项一致，最终 sent=20。该实验使用归档 Flink 输出，不宣称本轮重新执行了 Flink 作业。

此机制提供至少一次投递，接收端必须按 Idempotency-Key 去重。SQLite WAL 限本机磁盘，不能据此宣称多节点高可用或分布式精确一次。

### Redis 与 Webhook 的持久化重试集成

队列、Kafka 入队入口与 worker 均新增可选 `--redis-url`。启用后队列绑定 Webhook 与 Redis URL 的组合哈希，口令不写入 SQLite；不同目标、不同 Redis DB 或开启/关闭缓存都不能沿用原队列的已确认记录。原 Webhook-only 队列保持兼容。改变目标应新建独立队列并显式确定重放范围，不要把旧文件当成新的成功记录。

每次投递先 Redis SET（TTL 86400 秒），再 HTTP；只有两者都成功才标记 sent。连接/超时失败按队列策略重试，认证或 Redis 响应错误进入 dead，错误记录只保留异常类型，不记录口令。Redis 客户端内部重试关闭，使用 5 秒连接超时、10 秒读写超时，由队列统一计数。Webhook 失败后下一次会重写同一 Redis key 并刷新 TTL，不保证两套外部系统原子提交。


### 队列诊断与进程监管

`streaming/outbox_inspect.py` 使用 SQLite 只读连接和一致性事务，不需要 Webhook/Redis 地址，也不执行重试、重新入队或通知。输出各状态数量、到期待重试数量、过期租约数量，以及按状态/ID 筛选的消息状态和审计事件。默认最多 50 条，范围 1–1000；另返回总匹配数。诊断不包含告警载荷或目标口令。路径不存在时退出，不会创建空数据库。

```powershell
python -m streaming.outbox_inspect --db D:/industrial_energy_analysis/output/alerts/redis-queue.sqlite
python -m streaming.outbox_inspect --db D:/industrial_energy_analysis/output/alerts/redis-queue.sqlite --state dead --limit 100
python -m streaming.outbox_inspect --db D:/industrial_energy_analysis/output/alerts/redis-queue.sqlite --id <告警ID>
```

`streaming/outbox_supervisor.py` 是前台进程监管入口，只构建已知 worker/consumer 命令；配置中的数据库、日志路径必须绝对路径，目标 URL 从指定环境变量读取。样例为 `streaming/outbox_worker.example.json` 和 `streaming/outbox_consumer.example.json`，默认对应 Redis 队列；WebHook-only 队列须去掉 redis_env，不能混用原绑定目标。

```powershell
# 先设置已授权的本机或真实目标，并确保与原队列绑定值完全一致。
```

子进程非零退出时按 1、2、4…秒延迟重启，单次间隔上限 30 秒，默认至多 5 次重启（总启动 6 次）；正常退出不重启。达到上限后监管入口返回非零，需要人工检查日志。Ctrl+C 结束监管及其直接子进程；日志和退出记录写入配置指定的 D 盘目录。这里只监测进程退出，不监测业务吞吐；坏 Kafka 消息可能导致有限次重复退出，但不会自动跳过消息。worker 突然退出留下的在途记录仍遵守 60 秒租约恢复。
