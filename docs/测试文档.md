## 1. 测试策略总览

### 1.1 要防的是什么

这个项目**没有复杂的业务逻辑**，但有一个突出的风险：**数字会在改动后静默漂移**。
改装载逻辑、改表结构、改口径视图，代码都不会报错、不会崩，只是数字变了。
如果没有护栏，这种漂移会一路滑到论文和答辩现场。

所以测试的首要目标不是"证明代码能跑"，而是**"改动让数字变了就立刻报错"**。

### 1.2 四层结构

测试按**"离被测对象的距离"**分四层，每层解决上一层解决不了的问题：

| 层 | 文件 | 用例数 | 需要库 | 速度 | 回答什么问题 |
|---|---|---|---|---|---|
| **单元** | `test_clean_data.py` | 38 | 否 | ~6s | 单个清洗函数对每类脏数据的行为对不对？批次切片是不是全量的子集？ |
| **文档一致性** | `test_metric_dictionary.py` | 20 | 否 | ~0.02s | 字典有没有跟着代码偷跑？ |
| **回归快照** | `test_analysis_snapshot.py` | 3 | 是 | ~17s | 29 条查询的每一行数字还对不对？ |
| **装载一致性** | `test_import_mysql.py` | 9 | 是 | ~20s | 幂等 / 断点续跑 / 历史修正 / 水位线推进对不对？ |
| **端到端** | `test_end_to_end.py` | 16 | 是 | ~16s | 整条管道串起来产物齐不齐、数字自不自洽？ |
| **编排端到端** | `tools/verify_dag_run.py` | — | 是 | 数十秒 | 经 Airflow 调度跑，五个 task 是不是全 success？ |

**合计 121 个用例**：65 离线 + 56 需数据库（含 16 端到端，其中 19 项标了
`slow`）。另有一个手动的编排层验收脚本。

> **端到端测试的 `PIPELINE` 与 DAG 有一处刻意的分歧。** DAG 里 `load_warehouse`
> 走 `--incremental`（生产路径），而 `test_end_to_end.py` 用 `--init --full`。
> 理由是两者的目标不同：生产要的是"只装新的"，端到端要的是"**从零可复现**"——
> 它必须能在一个已有水位线的库上重跑并得到完全相同的结果。`--init --full` 是唯一
> 不依赖历史状态的组合。
>
> 这个分歧必须被记住，否则水位线落地时会出现"改了 DAG 却漏改测试"——
> 实测就是这样：`--init` 单独使用被运行期拒绝后，端到端 15 个用例一起报错，
> 而**离线测试全绿**，因为它们不碰装载路径。

### 1.3 默认只跑离线测试

```bash
pytest                                    # 离线, 不需要数据库, ~0.7 秒
MYSQL_PORT=3307 pytest -m db              # 数据库测试
MYSQL_PORT=3307 pytest -m "db and slow"   # 端到端(会重跑整条管道)
python tools/verify_dag_run.py            # 经 Airflow 触发 DAG
```

`pytest.ini` 里 `addopts = -m "not db"`，所以克隆仓库后 `pytest` 直接全绿，
**不要求先起 MySQL**。带 `-m db` 的测试连不上库时**跳过而非失败**——数据库
没起来属于"环境不具备"，不是"代码有问题"，报成失败会发出误导性的红。

> **一个真实的坑**：本机 3306 的 MySQL 可能是**陈旧的**（缺新视图、数字停在旧值），
> 而基线测试连的是 Docker 映射的 **3307**。两者混用会让人把"库是旧的"误读成
> "数字真的漂了"。**基线测试一律用 3307**。这个坑踩过两次，两次都被误判为回归。

## 2. 单元层：`test_clean_data.py`（38 项，离线）

### 2.1 为什么测函数而不是测 `main()`

清洗规则是**纯变换**（输入 DataFrame → 输出 DataFrame），`main()` 把"读文件→
写文件"也包进来了。测函数又快又准，失败时一眼看得出哪条规则坏了；测 `main()`
必须动磁盘，且失败信息被 IO 细节淹没。

### 2.2 覆盖的五个类

| 类 | 项数 | 对应哪类脏数据 |
|---|---|---|
| `TestNormText` | 6 | 半角/全角/零宽空格 —— 肉眼与半角无异，但会让 SQL 聚成两行 |
| `TestParseDates` | 6 | 4 种日期格式混用 |
| `TestBuildCalendar` | 7 | 节假日历：覆盖完整、日期唯一、周末标记与 `day_of_week` 一致 |
| `TestAliasTables` | 5 | 别名表完整性 + 已知错别字映射 + **无冲突目标** |
| `TestCleanArtifacts` | 11 | **产物级**断言：业务键唯一、无负值、无缺失、费用 = 量×价、单位规范 |
| `TestIncrementalBatch` | 3 | **批次落盘**：批次行是全量的逐字节子集、批次模式不动全量产物、窗口边界正确 |

### 2.3 `TestCleanArtifacts` 是产物回归基线

前四类测的是函数行为，这一类测的是**清洗产物的最终状态**——它不关心用什么
函数实现的，只断言"产出必须满足的业务约束"。所以它是**回归基线**：表结构或
清洗顺序改了，只要产物仍然合法就通过；一旦产物坏了就红。

**一条重要的历史**：`test_outlier_cells_are_imputed_not_dropped` 是**为案例 1
专门加的**。清洗阶段曾用整行删除处理离群值，导致 34 个格子永久缺失且插补
从不触发。这条断言（离群格子必须回到事实表且被补成正常量级）如果当时的代码
退回整行删除，会立刻变红。同类还有 `test_no_workshop_day_loses_an_energy_type`
（品种数不得少）和 `test_no_missing_consumption`。

### 2.4 `TestIncrementalBatch`：守"增量不改变口径"

这一类是**增量装载配套**加的，三条都通过 `subprocess` 真跑 `clean_data.py`（带
不同 `--batch-*` 参数），而不是直接调函数——因为要验的正是"落盘行为"，函数级
测不到。

| 用例 | 守什么 |
|---|---|
| `test_batch_slice_is_exact_subset_of_full` | 批次行按业务键合并回全量后，**每个非键列都必须逐字节相同**。这是核心那条：若有人把窗口筛选提前到读数据之前，离群判决用的 Q1/Q3 和插补用的中位数都会变，此测立刻红 |
| `test_batch_mode_does_not_touch_full_artifacts` | 批次模式**不得改写**四个全量产物。防止"顺手把批次结果也写到全量文件名"这类事故 |
| `test_batch_window_is_respected` | 批次行数 == 全量中 `record_date` 落在窗口内的行数。守的是别把边界写成开区间 |

用 `preserve_outputs` fixture 保证每个用例跑完把 `output/` 恢复原状——
否则这些测试会把 29 份基线依赖的产物改掉，制造"基线假红"。

## 3. 文档一致性层：`test_metric_dictionary.py`（20 项，离线）

### 3.1 守的是什么

`docs/指标字典.md` 是"指标定义"的唯一出处，论文和答辩都引用它。但**文档有个
天然缺陷：它不会跟着代码变**。改了折标煤系数、改了 CUSUM 的 h，代码跑得好好的，
字典却还写着旧值，而**没有任何东西会报错**。这份测试就是那个会报错的东西。

### 3.2 核心原则：从代码读真值，而不是从字典抄一遍

如果测试断言"字典里写的系数 == 一个硬编码在测试里的数"，那么字典改错了、
测试也跟着抄错。所以这里**从代码读真值再比对**：折标煤系数从
`create_table.sql` 的 `INSERT` 里解析出来，CUSUM 的 h 从视图定义里正则提取。

### 3.3 覆盖的四类

| 类 | 项数 | 守什么 |
|---|---|---|
| `TestFactors` | 3 | 6 个品种的折标煤/碳排系数；压缩空气碳排为 0 且**有解释**；当量值/等价值区分 |
| `TestCusumParams` | 4 | k=0.5 / h=9.9 与视图一致；白化按自然月；标定脚本存在且被引用 |
| `TestScopeAttribution` | 4 | 字典标注的口径与 SQL 实际条件一致（含**反向**断言） |
| `TestDocStructure` | 6 | 章节完整、单位齐全、NULL 语义、可加量契约、报告数字手写警告 |
| `TestMeasuredBaselineNumbers` | 3 | **口径速查表的基准值必须等于回归基线** |

### 3.4 两个值得说的设计

**`TestScopeAttribution` 的防错方向**：不只验"标注为剔除的查询真的写了剔除
条件"，还验"标注为仅连续型的 Q11/Q12 **不应**同时带剔除条件"。这一条**实测
抓出过一处不一致**：字典把 Q11/Q12 误归为"剔除公用工程"，而它们的 SQL 用的是
`is_continuous = 1`，语义不同（前者为了去重复计算，后者为了排除停产日干扰）。
两者在本数据集上结论恰好一致，所以**只能靠测试抓，靠人看不出来**。

**`TestMeasuredBaselineNumbers` 的边界**：字典里绝大多数实测值（占比、降幅）
**不该**写进测试——那些是某次运行的快照，换了数据就该变。但"口径速查表"里
那两个基准数字（全厂 / 剔除公用工程）不一样：它们是字典作为权威口径表的
**立论基础**，而且**有唯一正确答案**（就是 Q01/Q02 基线）。

> **判据**：一条断言该不该写，看这个数**有没有唯一权威来源**，而不是看它
> 是不是"实测值"。有权威来源的就必须锁。
>
> 这条断言是 #17 补上的。起因是发现字典速查表曾静默漂移：写着 `63,759.70` /
> `46,400.59`，真值是 `63,759.63` / `46,400.52`。**它躲过了全部 29 份回归基线**，
> 因为基线只锁 `output/Q*.csv` 的每一行，管不到 `docs/` 里手写的数字。
> 第三个用例 `test_no_stale_measured_values` 做反向断言，抓"改了速查表、
> 别处还漏了一处"。**已反向验证**：把值改回去，测试立刻变红。

## 4. 回归快照层：`test_analysis_snapshot.py`（3 项，需库）

### 4.1 守的是什么

29 条业务查询的**每一行数字**。基线在 `tests/baseline/`，是 2026-09-20 在固定
种子数据上跑出的 29 份结果快照，**已经过人工核对**——它们是"正确答案"。

### 4.2 比较策略

**逐行逐列比对，浮点按相对容差 `1e-6`**。不要求字节相同——CSV 里的浮点格式化
方式可能随 pandas 版本变化，那不是回归。但**行数、列名、行序**必须一致：它们
变了说明 SQL 语义真的变了。

`test_baseline_covers_all_queries` 和 `test_analysis_sql_query_count` 是两个
"元测试"：基线必须覆盖 29 条（少一条就是漏保护），且 `analysis.sql` 的查询数
必须与基线一致（防止新增查询却忘了建基线）。

### 4.3 三条使用纪律

**① 改完管道必须先重跑刷新产物，再去比基线。** 否则拿旧输出比旧基线会得到
**假的"全绿"**。判断方法：`ls -la output/Q01*.csv output/clean_energy.csv`，
Q*.csv 必须比 clean_energy.csv 新（这条判据现已自动化，见 §6.2）。

**② 基线报警时，先分清"数据陈旧"与"口径真变"**，两者的动作**相反**：

| 情形 | 判断依据 | 正确动作 |
|---|---|---|
| **数据/环境陈旧** | 说不出数字为什么该变；重新装载后差异消失 | **重新装载**，基线不动（因为不需要动）|
| **口径有意变更** | 能逐条说清每个数字为什么该变、变了多少 | **更新基线**，并在提交信息写明原因 |

"别用刷新基线把问题盖过去"防的是**说不出原因**的情形（那是 bug，不是基线
过期）。但反过来说，确认了口径变更却不敢更新基线，红线会一直红着、**红线本身
也就失效了**——两者混为一谈是另一种失败。详见 `问题发现与工程复盘.md` 案例 4。

**③ `ORDER BY` 必须是全序。** 基线是逐行比对，所以 `ORDER BY` 只写一个可能
并列的值（如 `ORDER BY Z值 DESC`）会让行序在两次跑之间漂移，甚至改变 `LIMIT`
截到谁。全部 29 条 `ORDER BY` 现已补上唯一键做次序键。

## 5. 装载一致性层：`test_import_mysql.py`（9 项，需库）

### 5.1 守的四个目标

1. **幂等**：同一批数据连续装载两次，记录数与能耗总量不变。
2. **历史修正**：修改一条历史记录后重新装载，数据库正确更新；且**重放过期
   数据时，已有的新值不得被改回去**。
3. **断点续跑**：装载中断后重跑，最终结果与一次完整装载一致。
4. **水位线语义**：推进、不倒退、空批次不动。

### 5.2 目标 2 曾长期是 `xfail(strict)`

第一阶段用的是 `LOAD DATA ... IGNORE`。`IGNORE` 的语义是"冲突时**保留已存在
的行、丢弃新来的行**"——历史修正会被静默丢弃。当时把这条标成 `xfail(strict)`
（预期失败），**而不是删掉或改成断言成功**。

这是刻意的：`xfail(strict)` 让"这个缺陷存在"变成**可执行的记录**——一旦
upsert 落地、该用例意外通过，`strict` 会让测试**报错**，提醒你去移除标记。
upsert 实现后标记已移除，用例转正。

> 这比写一句注释"历史修正暂不支持"强得多：注释不会在你修好之后提醒你更新它。

### 5.3 水位线三条（`test_watermark_*`）

| 用例 | 守什么 |
|---|---|
| `test_watermark_advances_within_load_transaction` | 水位线确实被写入，且取值等于**表内实际最大值**（不是 CSV 里的）。同时走一遍"`commit=False` 装载 → 推进 → 统一 commit"这条与生产同构的路径 |
| `test_empty_batch_does_not_move_watermark` | 空批次（`MAX` 返回 `NULL`）时水位线**保持不变**，不被兜底值打回 1970。这是**静默的性能事故**而非正确性事故——数据不会错，但 19,006 行会每天白重装一遍，只有测试能钉住 |
| `test_watermark_ignores_older_replay` | 用旧值推进时水位线**不倒退**。与事实表 upsert 的 `GREATEST` 同一理由：补跑历史区间不该把进度拉回去 |

> **写这三条时发现的一个真实改进**：最初 `advance_watermark` 的单调性**只依赖调用方
> 把 `old_val` 传对**——它拿传入的值当比较基准，若调用方传了个过期的值，`GREATEST`
> 就兜不住。改成函数内部**重新从库里读一次已记录的水位线**，取
> `max(old_val, stored_val)` 作下界之后，"不倒退"才真正由函数自己保证，而不是靠
> 调用方守规矩。`test_watermark_ignores_older_replay` 就是在这个改动后写下的。

**这三条都做了类型归一化**：pymysql 读 `DATETIME` 返回 `datetime` 对象，而
`advance_watermark` 的入参出参都是字符串。最初直接在断言里比较两者，红得毫无信息
（`datetime(2025,12,31,19,21) != '2025-12-31 19:21:00'`），掩盖了真正的语义断言。
`_watermark()` 辅助函数统一转成字符串再比。

## 6. 端到端层：`test_end_to_end.py`（16 项，需库，`slow`）

### 6.1 为什么需要它——前三层都够不到的地方

- `test_clean_data.py` / `test_metric_dictionary.py` 是**单元级**，不跨步骤。
- `test_analysis_snapshot.py` 逐行比对 29 条查询，**但它只读 `output/Q*.csv`，
  不关心这些 CSV 是"哪一次"跑出来的**。

于是有盲区：**每一步单独看都对，但步骤之间的衔接错了**。真实踩过的两类：

- **张冠李戴**：`report.html` 是用上一轮的 `Q*.csv` 生成的，而 `Q*.csv` 又是用
  上上轮的 `clean_*.csv` 生成的。每个文件本身都"合法"，拼起来却是一份不属于
  同一次运行的报告。
- **产物缺失/陈旧**：某个 `Q*.csv` 没生成成功，或时间戳停在上一轮，而回归基线
  恰好因为环境不同步也跟着"绿"了——假象。

**这份测试回答的是回归基线回答不了的问题**："这些产物是不是同一次跑出来的、
是不是全都在？"它**不重复**逐行比数值的工作（那是快照层的活）。

### 6.2 四个类

| 类 | 项数 | 断言 |
|---|---|---|
| `TestPipelineCompletes` | 5 | 五步全成功；`clean_report.txt` 非空；29 份 CSV 齐全；脚本自述"完成 29/29"；报告内联数据键齐全 |
| `TestArtifactFreshness` | 2 | `Q*.csv` 比 `clean_*.csv` 新；`report.html` 比所有 `Q*.csv` 新 |
| `TestThreeWayConsistency` | 7 | Q01 == Q28 求和 == 报告首屏（能耗/费用/碳排三项）；Q28 == Q29；报告 `tce_ex` == Q02；筛选锚点 == 立方体首末日 |
| `TestAgainstBaseline` | 2 | 端到端跑出的 Q01 仍等于基线；基线必须 29 份 |

**为什么"29 份 CSV 齐全"要单独测，不能只靠退出码**：`import_mysql.py` 是
"单条查询失败不中断整批"的设计——它会继续跑完并打印"完成 N/29"，但**退出码
仍是 0**。所以必须显式数文件，并对照脚本自述的计数（两者不一致说明有查询静默
失败但留下了旧文件）。

### 6.3 三路自洽是核心不变式

```
路径 A  Q01 直接聚合事实表
路径 B  Q28 车间日立方体求和        (前端 KPI 卡的底座)
路径 C  report.html 内联 JSON       (报告首屏显示的数)
```

**A == B** 证"立方体没丢行/多行"；**B == C** 证"报告用的就是这份立方体，不是
上一轮的"。任何一步衔接错位，这三条就会分叉。实跑四路（含前端 KPI 底座）
全是 `63,759.63`。

### 6.4 两个实现要点

**测试不污染工作区**：管道脚本的输出路径是**写死的**（没有可配置的输出目录），
所以测试自己备份 `data/` + `output/`，跑完原样还原。

> **一个踩到的坑**：最初复用 `conftest.py` 的 `preserve_outputs`，
> 但它是 **function-scoped** 的——**每个测试函数结束后就把产物还原成旧的**，
> 而模块级缓存还留着新跑的日志，断言的依据与磁盘对不上，表现为**随机失败**。
> 改成 module 作用域自己备份/还原后稳定（连跑两遍 16/16）。
>
> **判据**：备份夹具的作用域必须匹配"产物要被读多久"。

**报告 JSON 的提取方式**：`make_report.py` 生成时把整个占位区间（**含
`/*__END__*/` 标记本身**）替换成 JSON，所以产物里**只剩起始标记**
`/*__DATA__*/`。提取要用**括号配平扫描**出 JSON 结尾，不能找结束标记，
也不能找 `;`（字符串里可能带分号）。

## 7. 编排端到端：`tools/verify_dag_run.py`（手动）

### 7.1 与 `test_end_to_end.py` 的分工

| | `test_end_to_end.py` | `verify_dag_run.py` |
|---|---|---|
| 跑什么 | 顺序调四个脚本 | **经 Airflow 调度**跑同一批脚本 |
| 验什么 | 产物齐全 / 新鲜 / 三路自洽 | 同上 **+ 五个 task 全 success** |
| 速度 | ~16 秒 | 数十秒（含调度器轮询）|
| 进 CI | 是 | 否，手动 |

前者证明**代码链路**对，后者证明**编排链路**对——DAG 里 task 依赖顺序、容器内
`cd` 到对的目录、路径映射、retries 配置，都是前者够不到的。

**判据**：改的是脚本 → 跑 pytest；改的是 DAG / `docker-compose.yml` / 容器路径
→ 跑 `verify_dag_run.py`。

### 7.2 为什么走 CLI 而不是 REST API

默认的 `airflow.api.auth.backend.session` 只认浏览器会话，REST API 一律返回
**401**。要开 API 就得往 `docker-compose.yml` 加 `AIRFLOW__API__AUTH_BACKENDS`
——那是**为了验收而改被测系统的配置**，验收脚本不该有这个副作用。

走 `docker exec <scheduler> airflow ...` CLI 不需要任何配置改动，且验的正是
生产路径（调度器自己派发任务）。

### 7.3 它被反向验证过

一个验收脚本如果只会打绿勾，它就没有价值。`verify_dag_run.py` 经过两次破坏性
验证：

| 注入的缺陷 | 期望反应 | 实际 |
|---|---|---|
| 删掉 `Q23_*.csv` | 报"29 条查询的 CSV 全部生成"失败，点名缺失 Q23 | ✓ |
| 把报告首屏 `tce` 改成 `12345.67` | 报"Q01 == 报告首屏"失败，差 51413.96 | ✓ |
| 把 DAG 置为 `paused` 再运行 | 触发前自动 unpause，不空等超时 | ✓ |

## 8. 环境与运行

### 8.0 本机实测记录（2026-09-21）

全套四层在 Docker Desktop 冷启动的容器上重跑过一遍，**exit code 均为 0**：

| 层 | 命令 | 结果 |
|---|---|---|
| 离线 | `pytest` | `62 passed, 53 deselected` (0.53s) |
| 装载 + 快照 | `MYSQL_PORT=3307 pytest -m "db and not slow"` | `37 passed, 78 deselected` (14.2s) |
| 端到端 | `MYSQL_PORT=3307 pytest -m "db and slow"` | `16 passed, 99 deselected` (13.5s) |
| 编排 | `python tools/verify_dag_run.py` | 5 个 task 全 success；四路数字均 `63,759.63` |

三次冷启动重跑 `db` 层都是 37/37。**结果与基线一致，无回归。**

> **两个坑（都是这次重跑才暴露的，值得记下来）**
>
> **① 别把输出管进 `tail`，否则假绿。** `python tools/verify_dag_run.py | tail -40`
> 的退出码是 **`tail` 的**，不是脚本的——脚本 `fail()` 明明 `SystemExit(1)`，
> 管道整体仍报 exit 0。第一次真失败（下表第一行）就是这样被当成成功的。
> 要么重定向到文件再 `echo $?`，要么 `set -o pipefail`。
>
> **② 冷启动容器里 DAG 默认是 paused 的**，触发的 run 会**永远停在 `queued`**。
> 脚本原先只有一条 900 秒超时后报"run 仍未结束"的兜底——**指向管道卡住，
> 真因（忘了 unpause）要翻 UI 才看得到**。现已加 `ensure_unpaused()`：触发前
> 先查 `is_paused`，是则自动 unpause 并打印一行说明。已双向验证：paused 时
> 自动放行、未 paused 时不多余动作。

### 9.2 已知缺口（如实列出）

1. **前端筛选引擎的深层逻辑不在 pytest 里**。`TestThreeWayConsistency` 验的是
   报告内联数据与查询口径一致，但**浏览器里的聚合逻辑**由
   `tools/verify_filter.mjs`（9 组筛选下断言立方体 == KPI == 日汇总）和
   `tools/check_filter_ui.py`（Playwright 驱动真实页面）覆盖——这两个也是手动
   脚本，不在 `pytest` 内。
2. **报告正文数字无法自动核对**。讲结论的段落是**手写死的**，改数据后必须
   逐个核对。`test_end_to_end.py` 能锁住报告内联的 JSON，但锁不住段落里的
   中文数字。这是 `指标字典.md` 维护约定里明确警告过的风险类别。
3. **不校验字典里的推导性实测值**（如"天然气占比 49.24%"）。理由见 §3.4——
   它们没有唯一权威来源，写进测试只会变成需要天天维护的假绿。
4. **`tools/verify_dag_run.py` 未进 CI**。它依赖 webserver 在跑且较慢，目前手动。
5. **装载没有 deadlock 重试**。`src/import_mysql.py` 只对"服务端不允许 LOCAL
   INFILE"这一种 `OperationalError` 降级重试，**1213 (Deadlock) 不重试，直接抛**。
   实测在 MySQL 容器**刚建出来、缓冲池还冷**时跑整套 db 测试，`test_reload_is_idempotent`
   撞到过一次 1213；此后同一环境连跑 10 轮（含 3 次 `down -v` 全新重建）**均未再现**。
   判断是**冷启动期的一次性竞态**，不是稳定缺陷，因此**没有加盲重试**——按
   "不为不会发生的场景加处理"的取舍，加一个从未生效的重试分支只会是死代码。
   但**如实记在这里**：若日志里再次出现 1213，它就是这个点，而不是数据问题。
6. **没有性能测试**。管道全量跑约 15 秒（不含调度轮询），数据量小，性能不是
   当前瓶颈；但这也意味着**规模上去之后的行为未经验证**。
7. **没有对 `generate_data.py` 的规律做正向断言**。测试验的是清洗能正确处理
   注入的脏数据，但"生成的季节性/待机规律是否符合预期的物理机理"没有独立
   检验——它间接由下游异常检测的结论合理性佐证。
