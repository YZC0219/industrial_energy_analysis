# 阶段二：预测与智能归因

## 目标与原则

在 2σ、产量基线和 CUSUM 之外增加预测能力，但不以单一深度学习模型替代统计检测。所有模型使用相同特征口径、相同滚动时间窗口和相同指标比较；归因摘要必须能追溯到指标字典、SQL 结果和异常证据，禁止补写证据之外的原因。

## 实验矩阵

| 模型 | 角色 | 输入 | 状态 |
|---|---|---|---|
| 季节性朴素基线 | 最低可接受基准 | 同车间 7 日滞后 | 已落地 |
| LightGBM | 非线性表格基准 | 统一特征表 | 已落地 |
| LSTM | 序列模型对照 | 28 日历史窗口 | 已落地 |
| Transformer | 长依赖对照 | 28 日历史窗口 | 已落地 |
| 2σ / 产量基线 / CUSUM | 可解释检测基准 | 现有 SQL 结果 | 保留 |

滚动验证必须按时间前后切分，禁止随机划分。每个折只允许使用训练截止日以前的数据拟合；统一报告 MAE、RMSE、样本量、逐折训练/测试行数、训练业务键 SHA-256 和预测明细。先跳过共同的 28 日特征预热期，再取 365 日训练期和完整 30 日测试折；尾部不足 30 日的日期不计分。深度序列可以在历史上下文中包含预热 NaN，但目标行资格与表格模型一致，缺失历史值在仅由训练窗口估计的标准化后置零。`train_days`、`test_days` 都是连续自然日，特征构建和切折两处都会拒绝日期缺口。

告警提前量定义为“模型首次有效预警时间到经确认事件 `onset_time` 的时间差”。真值来源只能是维护记录、操作员确认或模拟场景预先写入的 ground truth；Q22、Q24、2σ、CUSUM 和预测残差都是待比较的检测器，不能互相充当真值。契约位于 `ml/schemas/incident_label.schema.json`。当前数据没有合格标签，所以指标输出 `null` 和 `unavailable_no_verified_incident_labels`，而不是编造提前量。

## 统一特征

`ml/feature_pipeline.py` 从清洗后的能耗和产量明细生成“车间×日”特征：产量、气温、周末/月度周期、能源价格指数、生产/低负荷/停产状态占比、目标滞后与滚动均值。`low_load_share` / `shutdown_share` 是**能源明细行占比**（分母为该车间日的能源行数），不是时间占比；其原始状态来自事后记录，只以 `t-1` 滞后值作为特征，并在指标可用性中单列为 `retrospective_energy_row_status_share`。当前数据没有生产计划、天气预报或预测时点设备快照，因此实测产量、实测温度、价格指数统一滞后一天；当天只使用事先可知的日历特征。所有目标历史统计同样先 `shift(1)` 再滚动，防止把当天实绩泄漏给当天预测。

Airflow 与 GitHub Actions 共用 `tools/run_phase2.py`，显式读取 `clean_batch_energy.csv` / `clean_batch_production.csv`，重建特征和模型并运行验证。SHA-256 provenance 清单绑定本次两个输入与特征、预测、metrics（以及可选深度产物）的内容哈希；验证器检查清单与当前文件一致，再复算预测和指标，过期或来源错配会失败。

在 731 个连续自然日上，模型先使用共同 28 日预热期，再以 365 个日历日训练、30 日测试、30 日步长滚动；只保留完整测试折，共 11 折、每折 240 条车间日预测，末尾 8 个自然日不计分。总 MAE/RMSE 是 2,640 条测试行的微平均，逐折 MAE/RMSE、训练/测试行数保存在 `ml_model_metrics.json`。既不能把逐折结果误读成月份等权平均，也不能把总体微平均排名误读成逐折稳定的胜负。各模型训练目标行数、训练键摘要和滚动测试键必须逐折相同，验证器会对产物中全部模型检查这项契约。当前新口径总体结果为：季节基线 `0.7550/1.3300`、LightGBM `0.4674/0.7750`、LSTM `0.5213/0.8538`、Transformer `0.5448/0.8415` tce（MAE/RMSE）。不能用该结果推断告警提前量。

逐折 MAE 从 `0.2946` 到 `1.2692`，最大值约为最小值的 4.3 倍；相比之下，LightGBM 与 LSTM 的总体 MAE 只差 `0.054`。LSTM 在第 5、6、7、9 折低于 LightGBM，Transformer 在第 1 折也低于 LightGBM。因此证据只支持“LightGBM 在本数据、本切分的总体微平均上略优”，不足以支持“表格模型普遍优于序列模型”或“LightGBM 每折均优”的结论。折间差异与季节相位同时变化，但当前实验没有隔离季节、训练窗增长等因素，故这里只描述波动，不把它直接解释为季节因果效应。

LSTM 与 Transformer 使用同一组滚动测试键、目标行资格、28 日序列、车间身份、固定随机种子和 12 个 epoch。每天在已观测到前一日真实值后预测下一日，属于滚动单步预测；没有把单步指标描述成一次性多日递归预测。模型优劣只引用本次 provenance 绑定的运行产物及逐折结果，不复用旧快照数字。`tools/verify_deep_artifacts.py` 会逐模型复算指标并确认每折目标训练行、键摘要、测试日期、车间、折号和训练截止日与基线完全一致。

Torch 放在 `requirements-deep.txt`，避免普通报表 CI 每次下载大型依赖。Airflow 中的 `run_deep_validation` 默认跳过，部署 Torch 后设置 `DEEP_LEARNING_ENABLED=1` 才运行并立即校验产物；`.github/workflows/deep-model-benchmark.yml` 提供可手工触发的独立复现实验和 30 天证据工件。

## 智能归因证据边界

RAG 助手仅允许检索三类来源：

1. `docs/指标字典.md` 中的口径与定义；
2. `output/Q*.csv` 中的 SQL 结果；
3. 2σ、产量基线、CUSUM 与预测残差产生的异常证据。

每个归因结论必须返回来源文件、记录键/指标名和证据值。没有证据时输出“证据不足”，不得根据行业常识虚构设备故障、人员操作或生产计划原因。`ml/attribution_assistant.py` 会保存问题、提示词、检索结果、引用和最终摘要；模型输出若引用本次检索结果之外的路径、记录或数值会直接失败。证据内容按不可信数据处理，其中出现的指令不会被执行。

归因输出契约位于 `ml/schemas/attribution_result.schema.json`：每条 claim 至少包含一个 citation，且来源类型只能是指标字典、SQL 结果或异常证据。默认离线模式是**检索与守卫回归的可复现替身，不是可用问答产品**：非因果问题会将排序第一条证据原文作为受控 claim，不理解问题、不会组织答案；summary 被刻意锁定为两条受控常量，避免在逐条引用之外夹带无来源结论。在线问答质量须在配置 `LLM_API_URL`、`LLM_API_KEY`、`LLM_MODEL` 并传入 `--use-llm` 后，使用覆盖检索命中正确性、问题相关性与证据不足场景的评测集单独验证。当前未把任何未运行的在线模型效果写入实验结论。

```bash
python -m ml.attribution_assistant "W04 停产日待机费用是多少"
```

在线端到端评测使用同一组固定用例和守卫；模型服务需兼容 OpenAI Chat Completions，并支持 JSON object 响应。配置 `.env.example` 中的变量后执行：

```bash
python -m ml.evaluate_attribution --use-llm --output output/attribution_eval_online.json
```

报告记录运行模式、实际 LLM 调用数、逐用例服务端/守卫错误、耗时、引用数、期望陈述命中和通过率。纯离线模式会将在线专用用例标为 `skipped_requires_llm`，不计为通过或失败；在线运行则必须调用模型并评分。任何服务错误、越界引用、无引用回答、错误拒答或关键陈述不匹配都会使命令以非零状态退出。GitHub Actions 的 `Online LLM attribution evaluation` 可手工触发；需先配置 `LLM_API_URL`、`LLM_API_KEY`、`LLM_MODEL` 三个仓库 Secret，评测产物无论成功失败都会保留 30 天。只有在线报告全量通过后，路线图中的助手任务才可标记完成。

2026-09-24 使用 DeepSeek API 完成在线验收：5/5 用例通过，通过率 1.0，总耗时 4.354 秒；其中 3 个用例实际调用在线模型，覆盖有证据的待机费用、CUSUM 证据选择和缺少维护记录时拒答，另 2 个明显越界问题由本地守卫直接拒答。结果保存在 `output/attribution_eval_online.json`，未记录 API Key。

实测离线受控模式会引用当前批次 `Q13` 中机加工车间的停产日、待机能耗和待机浪费字段；询问“为什么是设备故障”时则返回 `insufficient_evidence: true`，不会把异常信号扩写成设备根因。

固定评测集位于 `ml/evals/attribution_cases.json`，覆盖正确引用机加工车间待机费用字段、正确引用 CUSUM 且 claim 包含预期字段、拒绝设备根因臆测和拒绝未知车间等场景；成功回答必须有引用并命中预期实体与字段，避免只看“来源文件相同”，同时不把随数据批次变化的金额写死。`python -m ml.evaluate_attribution` 会在 CI 重跑并留存结果。

在线专用用例提问已知车间的设备检修日期。车间实体能在 SQL 证据中找到，但允许来源没有维护记录；该非因果问题不会被确定性因果词守卫短路，必须实际调用 LLM 并拒答，覆盖此前在线模型从未处理拒答的盲区。
