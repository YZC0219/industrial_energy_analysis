# 数据管道运行看板

运行看板位于 `http://127.0.0.1:8010/pipeline`，与 `/diagnostics` 共用本地分析 API，两个页面可以互相跳转。

## 启动与刷新

在项目根目录运行：

```powershell
python -m tools.collect_pipeline_status --serve
```

此入口启动本地网页服务，并每 60 秒读取主业务 CDC 的 Airflow 元数据库，将采集结果原子写入 `output/pipeline_status.json`。页面每 30 秒重读本地记录；“刷新记录”只重读，不触发批次。服务绑定本机地址，关闭启动进程后停止采集。

如果 8010 上已经运行现有诊断服务，更新并重启该服务后，在另一个终端只启动采集：

```powershell
python -m tools.collect_pipeline_status --interval 60
```

也可以不持续采集，运行 `python -m tools.collect_pipeline_status` 留存一次当前状态。通过进程变量 `ENERGY_OUTPUT_DIR` 可使用另一份产物目录；网页和采集器需指向同一目录。默认输出、测试和浏览器截图均在 D 盘。

## 展示内容及口径

| 内容 | 数据来源 | 判断边界 |
|---|---|---|
| 最近批次、三个任务步骤、失败位置 | `airflow_cdc_main` 中主 DAG 的运行与任务记录 | 采集时的状态，不触发或清除任务；超过 15 分钟标为过期 |
| 计划与实际时间、启动延迟 | 调度批次的 `data_interval_end` 与 `start_date` | 逻辑日期不等于计划启动日期；手动批次不计算延迟 |
| 任务耗时、尝试记录 | 保留的 TaskInstance 时间与 `try_number` | 不还原全部重试历史；执行中耗时截至证据采集时刻 |
| 最近成功完成、近 14 次批次 | 当前采集及 `mysql_cdc_business_main_daily_runtime_*.json` | 同一 run_id 按最近归档去重；历史成功不覆盖最新失败 |
| 当前批次逐字段对账 | `mysql_cdc_business_main_cutover_audit_*.json` 的 `cutover_evidence` | 必须对应同一批次归档且审计成功；未审计显示未知 |
| 基础环境 | 最新 `mysql_cdc_main_health_*.json` | 与批次采集独立；旧检查显示“当时通过”，不显示当前在线 |
| 本地报告 | `output/report.html` 文件修改时间 | 文件存在不等于报告消费该 CDC 批次；不作为同步完成证明 |

启动延迟不是源事件到报告的端到端同步延迟；目前没有足够证据计算后者。数据管道看板也不把模拟数据报告与 CDC 数仓视为自动相连。

环境检查使用现有只读工具，在确认实际部署目录后手动采集，例如本机已确认的部署：

```powershell
python -m tools.main_cdc_health --deployment D:/industrial_energy_analysis/tmp/cdc_main_daily_20261003103045
```

该检查读取 Docker、调度器、连接器及 VM/HDFS，并写独立健康证据。看板启动不会自动执行 SSH、触发数仓任务、重做对账或生成业务报告。

## 接口与验证

`GET /api/v1/pipeline` 返回上述状态投影，只包含展示需要的字段，不返回环境配置、密钥、原始错误或数据快照。采集失败会写入不可用状态，避免旧成功记录掩盖当前无法检查的问题。最新证据损坏时显示未知。

离线回归使用 `tests/test_pipeline_dashboard.py`，覆盖失败覆盖旧成功、审计批次匹配、证据过期、恢复去重、异常文件、报告独立性及采集失败。浏览器验收脚本为 `tools/verify_pipeline_browser.py`，不写业务数据或人工反馈。
